## تصحيحات يجب الحفاظ عليها عند إعادة الكتابة

- أرقام sequence وACK في TCP تتبع البايتات، لا أرقام الرسائل. ACK تراكمي، وليس شرطًا رد مستقل لكل packet. نافذة الاستقبال غير نافذة الازدحام، وليس نمو cwnd قانون مضاعفة دائمًا.
- عنوان IP وTTL من طبقة IP، لا حقول TCP. TTL في IPv4 حد قفزات عمليًا، وليس مهلة انتظار اتصال بالثواني.
- موثوقية TCP لا تعني ضمان وصول الطلب التجاري مهما حصل، ولا منع تنفيذه مرتين بعد retry. الإقرار بالنقل ليس إقرارًا بنجاح عملية التطبيق.
- TCP keepalive مختلف عن إعادة استخدام اتصال HTTP. وUDP ليس أسرع في كل تطبيق وكل ظرف.
- تصنيف IANA: system 0–1023، user 1024–49151، dynamic/private 49152–65535. الحد الأعلى 65535، وليس 65538 كما في الكراسة.
- شرح HTTP methods يستخدم PUT/PATCH للتعديل، لا method عامة اسمها UPDATE. يجب التمييز بين تمثيل HTTP/1.x النصي وHTTP/2 وHTTP/3، وعدم تعميم request line النصي عليهما.
- Stateless وصف لدلالة التفاعل؛ لا يعني اتصالًا جديدًا لكل request، ولا يمنع جلسة تطبيق مبنية على cookie.
- لا نُعلّم نموذج «العميل يشفّر session key بمفتاح الشهادة ثم الخادم يفكه» باعتباره وصف TLS الحديث عمومًا. نفصل النموذج التاريخي لـRSA key transport عن اتفاق المفاتيح، ودور التوقيع والمصادقة واشتقاق مفاتيح المرور. TLS 1.3 أزال static RSA key exchange.
- الشهادة وثقة CA والتحقق من hostname لا تضمن أن الموقع أمين تجاريًا أو أن تطبيقه بلا ثغرات. DV/OV/EV ليست درجات قوة تشفير متصاعدة.
- LB ليس شرطًا في كل نشر، وTLS قد ينتهي عنده أو عند reverse proxy أو يمتد للداخل حسب التصميم. PHP-FPM يدير workers ويتكلم FastCGI، وليس HTTP server بديلًا عن Nginx.
- رحلة الطلب ليست دائمًا خطًا جديدًا DNS ثم TCP ثم TLS: cache والاتصالات المعاد استخدامها وHTTP/3 تغير المراحل الفعلية.
