# مراجعة نقدية حادة لمحتوى المشروع

تاريخ المراجعة: 2026-09-26

## الحكم المختصر

المشروع واسع وطموح، وتغطيته التقنية أفضل من أغلب المذكرات التعليمية الفردية، لكنه **غير متجانس تحريريًا**. بعض مسارات C++ وPHP تبدو كفصول كتاب حقيقية، بينما أجزاء من OOP وDatabase وAuth تبدو كملخصات لموضوعات تحتاج شرحًا أعمق.

لا يصح وصف المشروع بأنه «مكتمل للمبتدئ» على مستوى كل درس. الوصف الأدق: **تغطية تقنية واسعة مع دروس ناضجة، لكن ما زالت هناك ديون تحريرية واختبارية واضحة.**

## نطاق المراجعة وأدلتها

- 236 ملف محتوى غير صفحات الفهارس: 118 زوجًا عربيًا/إنجليزيًا، إضافة إلى صفحتي reference.
- 195 ملفًا يحتوي code fences.
- 154 ملفًا يحتوي تمارين أو إجابات قابلة للفتح.
- 52 ملفًا يحتوي رسمًا توضيحيًا.
- 45 ملفًا فقط يحتوي قسمًا واضحًا للأخطاء الشائعة أو تصحيح المفاهيم.
- 9 ملفات فقط تذكر expected output بصياغة واضحة.
- 23 زوج درس تقل فيه النسخة الإنجليزية عن 70% من حجم العربية، وأربعة أزواج تقل عن 55%.

الملحق content-audit-inventory.csv يسجل المؤشرات لكل درس. الطول ليس مقياس جودة منفردًا؛ هو إنذار يوجه المراجعة البشرية.

## ما تم إصلاحه أثناء المراجعة

1. تحولت الرسومات من شكل خطي واحد إلى أربع لغات بصرية: pipeline مرقم، concept grid، cycle، وdecision flow.
2. استُبدلت العُقد العامة مثل “Overview / Core concepts / Worked example” بعُقد مرتبطة بالحساب والمنطق والقياس وخطة التعلم والعقلية الهندسية.
3. حُذف تكرار قسم كامل في درس C++ الإنجليزي الخاص بقواعد العمل.
4. حُذف تدريب مكرر في درس Ethernet وARP العربي.

## العيوب العامة مرتبة بالأولوية

### P0 — «قابل للتشغيل» غير مثبت بما يكفي

وجود code block لا يساوي مثالًا قابلًا للتشغيل. أغلب الأمثلة لا تعرض command كاملًا مع input وoutput المتوقع. المؤشر الحاد هو 9/236 فقط لوجود expected output واضح.

**المطلوب:** لكل مثال رئيسي: prerequisites، اسم الملف، command التشغيل، input، output، ثم تفسير سطر بسطر. لا يلزم ذلك لكل snippet صغير.

### P1 — النسخة الإنجليزية ليست نظيرًا مضمونًا للعربية

23 زوجًا أقل من نسبة 0.70. أسوأ أمثلة:

- auth/06-encryption-http-auth.md: النسبة 0.51.
- database/01-pdo-prepared-statements.md: النسبة 0.53.
- database/03-transactions-acid.md: النسبة 0.53.
- oop/01-classes-objects-encapsulation.md: النسبة 0.54.

هذا لا يثبت وحده فقد مفهوم، لكنه يجعل ادعاء تطابق النسختين غير موثوق من دون مقارنة فقرة بفقرة.

**المطلوب:** مصفوفة مفاهيم لكل زوج: كل تعريف ومثال وتحذير وتمرين في لغة يملك نظيرًا في الأخرى.

### P1 — أخطاء المبتدئ لا تُشرح بانتظام

45/236 فقط تحمل قسمًا واضحًا للأخطاء الشائعة. الدرس المبتدئ يحتاج أن يرى الكود الخاطئ، العرض الذي سيشاهده، سبب الخطأ، والإصلاح. سؤال في النهاية لا يعوض هذا.

**المطلوب:** إضافة “خطأ → لماذا حدث → كيف أراه → التصحيح” للدروس التي تتضمن syntax أو إعدادًا أو أمنًا.

### P1 — ترقيم وتنظيم Programming basics مربك

المسار العلوي يحتوي ثلاثة عناوين تحمل الرقم 8، ثم عناوين بأرقام متأخرة عن أسماء الملفات، وفجوة ظاهرة قبل 17. إصلاح العنوان فقط قد يخفي مشكلة URL وترتيب sidebar.

**المطلوب:** قرار بنيوي موثق: إما فصل “التفكير البرمجي” عن رحلة الويب، أو إعادة ترقيم الملفات والعناوين والروابط مع redirects. لا يُنصح بتغيير filenames بصمت.

### P2 — الرسومات كانت زخرفية أكثر من كونها تفسيرية

قبل الإصلاح كانت معظم الرسومات سلسلة صناديق متشابهة، وبعضها يعرض بنية الدرس بدل المفهوم. التنويع الحالي يحسن اللغة البصرية لكنه لا يكفي وحده.

**المطلوب لاحقًا:** labels على الأسهم عندما تمثل تحولًا، إظهار مسار الفشل والرجوع، استخدام مقارنة ثنائية لموضوعات مثل TCP/UDP وauthentication/authorization، وعدم وضع رسم لمجرد توحيد الشكل.

### P2 — التمارين متخصصة لكنها غالبًا قليلة

تم التخلص من القالب العام، وكل درس يملك exercise/answer وفق الفحص، لكن عددًا كبيرًا يملك سؤالًا أو سؤالين. هذا يقيس التذكر أكثر من التطبيق.

**المطلوب:** ثلاث طبقات: سؤال تفسير، debugging قصير، ومهمة بناء أو تعديل، مع expected behavior.

### P2 — المصادر والإصدارات غير منتظمة

الموضوعات المتغيرة مثل ميزات PHP 8.x وOAuth/OIDC وpasskeys وHTTP/3 تحتاج version markers وروابط أولية وتاريخ تحقق.

**المطلوب:** خانة “Verified against” موحدة للموضوعات المتغيرة، مع مصادر رسمية.

## نقد كل كارت

### Programming basics

- القوة: خريطة جيدة من URL حتى CDN وWAF، مع أساسيات الكمبيوتر والرياضيات.
- الضعف: لا توجد prerequisite graph، ويوجد تداخل بين “داخل الخادم” و“Server/Proxy/API Gateway”، وبين درس TCP المبكر وطبقات الشبكة اللاحقة.
- النقص: labs محفوظة النتائج تستخدم DevTools وDNS وHTTP، وتمرين نهائي يتتبع request عبر كل الطبقات.

### C++

- القوة: أفضل مسار من حيث العمق والحدود وdiagnostics والتدرج من المصدر إلى التنفيذ.
- الضعف: كثافة النص قد ترهق المبتدئ، وبعض الملفات تجمع موضوعات كثيرة في عنوان واحد.
- النقص: مشاريع صغيرة تراكمية وbuild commands موحدة لكل نظام وفصل أوضح للبرمجة التنافسية.

### PHP

- القوة: تغطية واسعة تشمل syntax والأنواع والملفات والويب والميزات الحديثة.
- الضعف: الدروس المتأخرة تميل إلى catalog للميزات؛ لا يظهر دائمًا متى لا تستخدم الميزة.
- النقص: تطبيق صغير يتطور عبر الدروس، tests قابلة للتشغيل، وoutputs وأخطاء فعلية من PHP CLI.

### OOP

- القوة: interfaces وtraits وDI وreadonly وmagic methods موجودة.
- الضعف: المفاهيم معزولة؛ قد يحفظ القارئ التعريف من غير رؤية refactoring كامل.
- النقص: مثال procedural سيئ يتحول عبر الدروس مع tests تثبت التحسن.

### Database

- القوة: PDO وORM وACID وisolation وschema/indexes/migrations.
- الضعف: لا توجد بيئة SQL أو dataset موحد؛ شرح isolation من غير تجربتين متزامنتين يظل نظريًا.
- النقص: schema قابل للتشغيل، EXPLAIN output، تجربة deadlock، وmigration آمنة خطوة بخطوة.

### PHP Runtime

- القوة: يغطي واقع التشغيل الذي تتجاهله دورات كثيرة.
- الضعف: يفترض معرفة Linux وprocesses وnetworking أكثر مما يعلن، وقد يخلط المبتدئ بين وصف المفهوم ووصفة production.
- النقص: prerequisite bridges، أوامر تحقق وoutputs، failure drills، وفروق development/production.

### Auth and authorization

- القوة: نطاق ممتاز من sessions حتى OAuth المتقدم وإدارة الأسرار والحوادث.
- الضعف: العمق لا يوازي حساسية الموضوع؛ بعض الدروس القصيرة قد تعطي ثقة زائدة.
- النقص: threat model ثابت لتطبيق واحد، رسوم protocol messages، negative tests، وحدود واضحة لما لا يجب بناؤه يدويًا.

## خطة الإصلاح

1. إضافة outputs وcommands للأمثلة الرئيسية، بدءًا من PHP وDatabase وRuntime.
2. معالجة 23 زوجًا تحت 0.70، بدءًا بالأربعة تحت 0.55.
3. توسيع Auth بسيناريو تهديد وnegative test ومصدر رسمي لكل درس.
4. مشروع تراكمي لكل من PHP وOOP وDatabase، ومختبر request واحد لـProgramming basics.
5. حسم ترقيم Programming basics مع redirects.
6. مراجعة بصرية ثانية وإضافة branch labels ومسارات failure حيث تقدم معنى.

### الحكم الحاد بعد الجولة

- **PHP وDatabase وRuntime:** أصبحت قابلية التحقق أفضل بوضوح، لكن بعض أوامر المختبر تفترض أن المتعلم سينشئ الملف المذكور من تعليمات الدرس؛ تحويلها إلى fixtures جاهزة واختبارات CI سيكون الدرجة التالية.
- **Auth:** صار كل درس يطلب إثبات أن الهجوم يفشل، وهو تصحيح جوهري. الخطر المتبقي هو أن الروابط الرسمية تتغير أو تتطور؛ يجب إعادة التحقق دوريًا.
- **OOP:** المشروع الختامي يربط المفاهيم، لكنه لا يعوض بعد مثال refactoring واحدًا يتطور فعلًا عبر الملفات الثمانية.
- **Programming Basics:** المختبر النهائي قوي، والمساران ذوا الرقم 8 أصبحا واضحين. ما زالت كثافة المسار الكلية عالية على مبتدئ، ويستحسن أن تعرض الواجهة المتطلبات السابقة كخريطة قابلة للنقر مستقبلًا.
- **C++:** رسوم القرار أصبحت أدق، لكن الخطة الأصلية ما زالت تصنف إعادة صياغة النبرة والتدرج الكامل كعمل تحريري غير منجز.

### ما لا يعنيه هذا الإغلاق

إضافة النقاط الناقصة تجعل النطاق المفاهيمي أقرب للاكتمال، لكنها لا تحول كل checkpoint تلقائيًا إلى fixture يعمل داخل CI. الدروس التي تطلب خدمات حقيقية مثل Redis وFPM وOAuth provider وKMS ما زالت تحتاج مختبرات تنفيذ منفصلة إذا كان المطلوب إثباتها آليًا داخل المستودع.
