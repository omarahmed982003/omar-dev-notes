# المرحلة 10 — Laravel من الأساس للمنتج

الإصدار: 1.1 — مراجعة المنهج 2026-10-21. مراجعة تحريرية؛ لم تبدأ الدراسة.

هنبني نظام حجز صغير server-rendered. كل ميزة بتبدأ بالمشكلة اللي بتحلها وبالمقارنة مع Plain PHP؛ Laravel مش قائمة أوامر Artisan ولا وصفة CRUD.

## المتطلبات وحدود المرحلة

نجاح بوابة OOP المحلية 9 ومشروع PHP/SQL في 8، وفهم HTTP و HTML والنماذج و Composer. سجل إصدارات PHP و Laravel و DB الفعلية وتوافقها من الوثائق الرسمية وقت المختبر.

كل 10.1–10.9 أساس إلزامي، لكن كل عنوان فرعي جلسة أو أكثر. الربط المتقدم بـ OOP و Laravel Query امتداد بعد الأساس، ولا يمنع دخول هذه المرحلة بسبب عدم إنهاء منهج قديم كامل.

## خطة الدراسة

### 10.1 — المشروع ودورة الطلب والإعدادات

- المستوى: أساسي إلزامي.
- المتطلبات: المرحلة 9 و Composer.
- الناتج: يتتبع request من public/index.php إلى response ويعيد تجهيز المختبر.

#### 10.1.a — لماذا Framework وما الذي يملكه المشروع؟

قارن routing و DI اليدويين بالـ skeleton. اقرأ directories و Artisan و bootstrap ومسار request/response حسب إصدار المختبر، دون حفظ رسم lifecycle قديم.

#### 10.1.b — Configuration و Environment والأصول

ميّز .env عن config وعن secrets و config cache. شغّل Blade/assets بأوامر المشروع و lockfiles؛ لا تجعل npm/Vite واجبًا غامضًا. أول smoke test يثبت الصفحة.

**تطبيق وتقييم 10.1 بعد الأجزاء السابقة:**

- تجربة صغيرة: route تعرض config غير سرية، و README يشغّل المشروع من clone نظيف.
- فشل متعمّد: إعداد قديم في config cache؛ شخّصه دون نشر .env أو طباعة secret.
- محاولة مستقلة: أضف إعداد feature بسيطًا واختبر قيمته في testing environment.
- دليل النجاح: نسخ المختبر وأوامر الإقلاع و smoke test ورسم request lifecycle.

### 10.2 — من الطلب إلىصفحة ونموذج صحيح

- المستوى: أساسي إلزامي.
- المتطلبات: 10.1 و HTML/HTTP.
- الناتج: يبني form يتعامل مع نجاح ورفض دون خلط المنطق بالعرض.

#### 10.2.a — Routes و Controllers و Middleware

ابدأ بـ route واحدة ثم controller صغير و middleware لمسؤولية مشتركة. تتبع route params و model binding و 404 و redirect؛ binding مش authorization.

#### 10.2.b — Validation و Form Requests

افصل شكل المدخل عن قاعدة العمل. استخدم server validation ورسائل مفهومة و old input و CSRF في النماذج؛ لا تسمح لحقل owner_id يحدد المالك.

#### 10.2.c — Blade و Views وعرض الأخطاء

Layouts و components صغيرة و escaping افتراضي، ثم عرض حالات فارغة وأخطاء. اربط assets الموجودة بدل إعادة شرح CSS؛ raw HTML له حدود ثقة.

**تطبيق وتقييم 10.2 بعد الأجزاء السابقة:**

- تجربة صغيرة: إنشاء حجز صالح ثم redirect وعرض خطأ validation مع بقاء المدخل.
- فشل متعمّد: تاريخ أو حقل مطلوب غير صالح وطلب بلا CSRF؛ لا يُنشأ سجل.
- محاولة مستقلة: أضف نموذج تعديل مع error bag وحالة empty مستقلة.
- دليل النجاح: اختبارات HTTP للنجاح والرفض و 404 وشرح موضع كل مسؤولية.

### 10.3 — Container و Providers و DI فقط

- المستوى: أساسي إلزامي.
- المتطلبات: 10.1 و DI اليدوي 9.4.
- الناتج: يبدل implementation من موضع الربط دون service locator داخل domain.

#### 10.3.a — Binding و Resolution

مرر BookingService عبر constructor، ثم اربط contract بتنفيذ. فسر auto-resolution وحدوده عند interface، ومتى provider يسجل الربط.

#### 10.3.b — Lifetime وحدود السحر

قارن transient و singleton و scoped حسب الإصدار ونمط التشغيل؛ لا تحتفظ بمستخدم request داخل singleton. فسر Facade الأساسية دون مساواتها بـ Facade Pattern.

**تطبيق وتقييم 10.3 بعد الأجزاء السابقة:**

- تجربة صغيرة: تبديل sender إلىتنفيذ اختباري عبر binding مع نفس المستهلك.
- فشل متعمّد: binding ناقص أو singleton يحفظ حالة مستخدم سابق؛ الاختبار يكشفه.
- محاولة مستقلة: أضف Clock contract واربطه بساعة ثابتة في اختبار.
- دليل النجاح: اختبارات resolution وتفسير lifetime والاعتماد الظاهر؛ لا استكمال مشروع OOP المعتمد على Eloquent هنا.

### 10.4 — تهيئة البيانات وكتابة Model بأمان

- المستوى: أساسي إلزامي.
- المتطلبات: 10.2 و SQL/constraints في 8.
- الناتج: يبني schema قابلًا لإعادة الإنشاء ويفصل Model عن كل قواعد العمل.

#### 10.4.a — Migrations و Seeders و Factories

ابدأ بمخطط bookings ومفاتيحه و constraints، ثم migration وبيانات تجريبية ثابتة. فرق seeders عن factories، ورفض تشغيل أوامر destructive على بيانات مهمة.

#### 10.4.b — Models و Persistence و Casts

ميّز query builder عن model instance، وناقش mass assignment و fillable/guarded و casts و timestamps. تحويل type لا يغني عن validation أو authorization.

**تطبيق وتقييم 10.4 بعد الأجزاء السابقة:**

- تجربة صغيرة: migration على DB تجريبية فارغة ثم seed وتشغيل create/read.
- فشل متعمّد: payload يحاول تغيير tenant/owner أو حالة حساسة؛ لا يُسمح بذلك.
- محاولة مستقلة: أضف جدول booking_items وعلاقة FK مع رفض orphan.
- دليل النجاح: migration و fixtures واختبارات constraints وحماية الحقول وتعليمات reset آمن.

### 10.5 — SQL ثم Query Builder ثم Eloquent

- المستوى: أساسي إلزامي.
- المتطلبات: 10.4 و JOIN و FK و PDO.
- الناتج: يتنبأ بالـ SQL وعدد queries ويختار أسلوب قراءة مناسبًا.

#### 10.5.a — بناء الاستعلام والعلاقات

نفذ طلبًا واحدًا Raw SQL ثم Builder ثم Eloquent مع نفس النتائج. اربط belongsTo/hasMany باتجاه FK، ثم many-to-many بمثال مستقل؛ لا تعرّف علاقة بلا schema.

#### 10.5.b — N+1 وحدود الذاكرة والكتابة

قارن lazy/eager loading وعدّ queries، وضع pagination و allowed filters/sorts. نفذ transaction صغيرة لقواعد الحجز؛ locks المتعمقة في 14.

**تطبيق وتقييم 10.5 بعد الأجزاء السابقة:**

- تجربة صغيرة: قائمة حجوزات وأصحابها دون N+1 مع حد للصفحة.
- فشل متعمّد: فلتر OR غير مجمّع يسرب بيانات مالك آخر أو علاقة معكوسة؛ اختبار يعزل السبب.
- محاولة مستقلة: أضف تقرير aggregate واختَر SQL أو Builder أو Eloquent مع تبرير.
- دليل النجاح: schema ونتائج متكافئة وعدّ queries واختبارات ownership و pagination؛ لا شرط إنهاء Laravel Query كاملًا.

### 10.6 — تسجيل الدخول والصلاحيات

- المستوى: أساسي إلزامي.
- المتطلبات: 10.2 و 10.5 وجلسات 8.
- الناتج: يحمي كل عملية وبياناتها على الخادم باستخدام آليات موثوقة.

#### 10.6.a — Authentication موثوقة ومفهومة

استخدم آلية Laravel مدعومة حسب الإصدار؛ تتبع session و guard/provider و login/logout/reset. تحقق من regeneration و CSRF ورسائل لا تسرّب وجود الحساب؛ لا تصمم crypto.

#### 10.6.b — Policies و Gates و Ownership

حدّد matrix صاحب/مستخدم آخر/مدير/زائر ثم deny by default. قارن policy بحماية route وبـ query scoping؛ إخفاء الزر مش authorization.

**تطبيق وتقييم 10.6 بعد الأجزاء السابقة:**

- تجربة صغيرة: مستخدم ينشئ ويقرأ حجزه ولا يقرأ أو يعدل حجز غيره.
- فشل متعمّد: تغيير ID مباشرة أو حقن owner_id أو طلب من زائر؛ لا تسريب ولا تعديل.
- محاولة مستقلة: أضف إلغاء للمالك في حالة محددة واكتب matrix اختبارات مستقلة.
- دليل النجاح: tests للنجاح والرفض وشرح الفرق بين authentication و authorization و business rule.

### 10.7 — الملفات والإشعارات والشغل المؤجل

- المستوى: أساسي إلزامي.
- المتطلبات: 10.4 و 10.6؛ timeouts و failure أساس.
- الناتج: يتتبع side effect من حدث تجاري لتخزين أو إشعار دون افتراض الموثوقية.

#### 10.7.a — Filesystem و Uploads

تحقق من الحجم والنوع على الخادم، أسماء عشوائية وتخزين private وتنزيل مأذون. قارن disk abstraction بالمسار الحقيقي و URL؛ لا تضع upload قابلًا للتنفيذ داخل public.

#### 10.7.b — Mail و Notifications و Events

رسالة تجريبية لمستقبل وهمي و notification channel واحد؛ فرق event/listener عن نداء مباشر. لا ترسل سرًا في mail أو log، ولا ترسل side effect قبل نجاح transaction.

#### 10.7.c — Jobs و Scheduler بمختبر محدود

استخدم sync أولًا ثم database queue محلية؛ trace enqueue/process/failure و restart worker. scheduler بوقت UTC ثابت هنا. Redis و delivery guarantees و DLQ تعميق 16–17، مش افتراضات مخفية.

**تطبيق وتقييم 10.7 بعد الأجزاء السابقة:**

- تجربة صغيرة: بعد commit أرسل تأكيدًا لصندوق mail محلي و job في DB؛ سجل ID قابلًا للتتبع.
- فشل متعمّد: ارفع ملفًا ضارًا أو أوقف worker؛ لا تنفيذ ملف ولا ادعاء وصول الإشعار.
- محاولة مستقلة: أضف تذكيرًا تجريبيًا مع فشل مزود وهمي وسجل حالة قابلة للتشخيص.
- دليل النجاح: اختبارات upload/download authorization و fake محدودة وملاحظة فعلية ل worker وعطلها.

### 10.8 — اختبارات المنتج والأخطاء والتكامل

- المستوى: أساسي إلزامي.
- المتطلبات: 10.1–10.7.
- الناتج: يثبت مسار حجز كاملًا ورفضه ويشخص عطلًا دون وصفة.

#### 10.8.a — Unit و Feature و Database Tests

اختبر قواعد مستقلة ثم request/DB مع fixtures معزولة؛ Mail/Queue/HTTP fakes لا تثبت سلوك الخدمات الحقيقية. حدّد integration test واحدًا يعبر حدودًا فعلية.

#### 10.8.b — Transactions و Exceptions و Logging

اجمع كتابة business operation في حد transaction المناسب، وافصل خطأ متوقع عن 500. سجل correlation ID بلا secrets؛ اكتب rollback test واختبار منع تسرب البيانات.

**تطبيق وتقييم 10.8 بعد الأجزاء السابقة:**

- تجربة صغيرة: حجز متعدد الخطوات ينجح كله أو يرجع كله بعد عطل متعمد.
- فشل متعمّد: fake يخفي عدم تشغيل worker أو كتابة جزئية؛ اختبار تكامل يكشف الحدود.
- محاولة مستقلة: أضف feature مستقلة وحل عطل ownership أو transaction من failing test.
- دليل النجاح: test suite قابلة للتشغيل و README و report يحدد ما تثبته fakes وما لا تثبته؛ يمكن الآن تطبيق امتداد OOP15–16.

### 10.9 — الوقت والتوطين في منتج حقيقي

- المستوى: أساسي إلزامي.
- المتطلبات: 10.2 و 10.4 واستخدام الكائنات في 9.1؛ هذه أول وحدة تطبيقية للوقت والتوطين.
- الناتج: يعرض مواعيد وأرقامًا مترجمة دون إفساد الوقت أو المال.

#### 10.9.a — DateTimeImmutable و UTC و DST

ابدأ بموعد محلي مع IANA timezone، ثم parsing صارم والتحقق منمدخل غير صالح، والتحويل للحفظ ووقت العرض. فرّق instant عن local wall time وعن recurring schedule؛ UTC وحدها لا تحفظ نية الموعد المتكرر.

#### 10.9.b — Localization و Plurals و Locale Formatting

ملفات ترجمة ومفاتيح و fallback و pluralization وتجربة عربي/إنجليزي. استخدم formatter موثوقًا ومتوافقًا مثل Intl/NumberFormatter للأرقام/العملة عند توفره؛ لا تبنِ مالًا بـ float ولا تخلط locale بـ timezone.

**تطبيق وتقييم 10.9 بعد الأجزاء السابقة:**

- تجربة صغيرة: اعرض نفس instant في Cairo و UTC مع لغة وتنسيق مختلفين، وجمع صفر/واحد/عدة بعقد واضح.
- فشل متعمّد: تاريخ مستحيل وموعد داخل gap/overlap لتوقيت DST في منطقة معروفة؛ طبّق سياسة رفض/اختيار معلنة لا تصحيحًا صامتًا.
- محاولة مستقلة: أضف تذكير حجز محلي واختبارات حول انتقال DST و fallback ترجمة.
- دليل النجاح: اختبارات ثابتة بمواعيد ومناطق مسجلة وشرح سياسة الالتباس وإثبات عدم تغير القيمة المالية بعد formatting.

## المشروع وبوابة الخروج

نظام حجز أو متجر صغير بواجهة Blade و accounts وصلاحيات و schema واختبارات و README قابل للتشغيل. القبول: happy path، ورفض مستخدم آخر، وحماية mass assignment/CSRF/uploads، و rollback لعطل كتابة، وعدّ queries، وإشعار محلي بعد commit، وتنسيق موعد صحيح. إضافة قاعدة جديدة مستقلة شرط. بعد 10.8 يمكن اختيار تطبيق OOP15–16 على نفس النظام، لكن لا يفرض إنهاء المالك كاملًا؛ لا مدفوعات أو بيانات عملاء حقيقية.

## تشغيل الجلسة والتقدم

اقرأ README.md و COMMON_RULES.md وهذا الملف وملف PROGRESS المجاور كاملين. اشرح بالعامية المصرية الطبيعية: المشكلة ثم الفكرة وآليتها ثم تجربة صغيرة وتوقع الناتج قبل التنفيذ. مفهوم واحد وسؤال واحد كل مرة؛ لا تعرض حل المحاولة المستقلة قبل محاولة الطالب. كل عنوان فرعي وحدة شرح، وليس درسًا موسوعيًا في رسالة واحدة.

الـ IDs المحلية تقيس أدلة هذا المنهج فقط. ملفات study القديمة مراجع وتعميق وليست شرط إتمام كامل قبل العبور. لا تنسخ درجاتها، ولا تعتبر نجاح بوابة محلية نجاحًا تلقائيًا في نقطة قديمة. إن اختار الطالب دراسة المالك كاملًا، اقرأ منهجه وتقدمه والتزم بترتيبه؛ سجل الربط دون ازدواج النتائج.

حدّث التقدم المحلي وفق الدليل الحقيقي: checkpoint والعنوان الفرعي وآخر تمرين مكتمل والخطوة غير المكتملة والاختبارات والفجوات. شرط النجاح 80% على الأقل مع أدلة مستقلة وإصلاح أخطاء الأمان أو صحة البيانات الجوهرية. المتقدم الاختياري لا يعطل بوابة الأساس، ولا يسجل Passed أو درجة وهمية إن لم يُدرس. لا نشر أو commit أو push أو تعديل لتقدم مسار قديم تلقائيًا.
