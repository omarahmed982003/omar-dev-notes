# المرحلة 9 — OOP وتصميم الكود

الإصدار: 1.1 — مراجعة المنهج 2026-10-21. مراجعة تحريرية؛ لم تبدأ الدراسة.

هنحل مشكلة تنظيم Task Manager اللي اتبنى بالفعل، مش نحفظ أسماء أربع pillars. هننقل سلوكًا واحدًا لكائنات لها مسؤوليات وحدود، ونثبت إن التغيير ماكسرش البرنامج.

## المتطلبات وحدود المرحلة

نجاح مشروع المرحلة 8، وفهم functions و arrays و exceptions وقراءة ملفات متعددة. لو الأساس ناقص نعمل remediation محددة؛ مش مطلوب إنهاء كل OOP Master القديم.

الأساس هنا Classes و Encapsulation والعلاقات والعقود و DI واختبارات التصميم. Reflection و Attributes وكل كتالوج Patterns تعميق اختياري لاحق؛ مش بوابة لدخول Laravel. أمثلة PHP من غير Framework أولًا.

## خطة الدراسة

### 9.1 — الكائن وحماية حالته

- المستوى: أساسي إلزامي.
- المتطلبات: functions و types ومشروع Plain PHP.
- الناتج: يحوّل قاعدة عمل إلى object يمنع الحالة غير الصالحة.

#### 9.1.a — Class و Object و State و Behavior

ابدأ بمهمة لها عنوان وحالة. قارن array مفتوحة التعديل بكائن له constructor و methods؛ اتتبع كائنين مستقلين ومرجعين لنفس الكائن، من غير اختزال object إلىجدول بيانات.

#### 9.1.b — Encapsulation و Invariants

حدّد القاعدة: عنوان غير فارغ وانتقال حالة مسموح. ضع التحقق في حد الكائن، وناقش visibility و readonly بحسب إصدار المختبر؛ getter/setter لكل خاصية مش حماية تلقائية.

**تطبيق وتقييم 9.1 بعد الأجزاء السابقة:**

- تجربة صغيرة: أنشئ مهمتين وغيّر حالة واحدة؛ الثانية لا تتغير.
- فشل متعمّد: حاول إنشاء عنوان فارغ أو تعيين الحالة من الخارج وتحقق من الرفض المتوقع.
- محاولة مستقلة: اكتب SpendingLimit يمنع قيمة سالبة وتجاوز حد محدد.
- دليل النجاح: كود مستقل واختبارات الحالة الطبيعية والرفض، وتفسير أين تفرض القاعدة.

### 9.2 — العلاقات والتبديل بعقود واضحة

- المستوى: أساسي إلزامي.
- المتطلبات: 9.1.
- الناتج: يفصل الاعتماد على سلوك مطلوب عن اسم implementation.

#### 9.2.a — Composition والعلاقات

ارسم من يملك من ومن يستعمل من، ثم مرر ReminderSender إلىخدمة بدل إنشاء كل شيء داخلها. قارن coupling و cohesion وسهولة التغيير.

#### 9.2.b — Inheritance و Polymorphism و Interfaces

ابدأ بالحاجة لتبديل sender، ثم interface وتنفيذين. قارن composition مع inheritance، وراجع عقد السلوك لا مجرد توافق signature؛ استخدم abstract class عند وجود سبب.

**تطبيق وتقييم 9.2 بعد الأجزاء السابقة:**

- تجربة صغيرة: بدّل ConsoleSender بتنفيذ يسجل الرسائل في الذاكرة من غير تعديل المستهلك.
- فشل متعمّد: تنفيذ يكسر العقد أو يرمي خطأ غير متوقع؛ اختبار المستهلك يكشفه.
- محاولة مستقلة: أضف Exporter بصيغتين يتعامل معهما نفس use case.
- دليل النجاح: رسم علاقات صغير واختبار لكل تنفيذ وتبرير عدم استخدام inheritance بلا حاجة.

### 9.3 — حدود الأنواع وتحميل الكود

- المستوى: أساسي إلزامي.
- المتطلبات: 9.1 و 9.2 و strict_types.
- الناتج: يشغّل مشروعًا صغيرًا بأسماء واضحة و value objects وعقد أخطاء.

#### 9.3.a — Types و Value Objects و Exceptions

اربط nullable و union و enum بحسب الإصدار بحالات domain حقيقية. اكتب TaskId أو Email بعد التحقق، وميّز رفض المدخل عن infrastructure failure؛ لا تحول كل string إلى class بلا مكسب.

#### 9.3.b — Namespaces و Composer و PSR-4

ابدأ بتصادم اسمين و require/bootstrap يدوي محدود، ثم autoload واحد. فسّر composer.json مقابل composer.lock، و install مقابل update؛ لا تنسخ dependency مجهولة.

#### 9.3.c — Callables و Closures في PHP

مرر callback صغيرًا للفلترة؛ قارن closure و use by value/reference و arrow function و invokable object. وضّح متى يحجب capture اعتمادًا مهمًا. Reflection و Attributes مراجع متقدمة اختيارية بعد الأساس.

**تطبيق وتقييم 9.3 بعد الأجزاء السابقة:**

- تجربة صغيرة: تشغيل CLI من root المشروع عبر vendor/autoload.php، وإنشاء Value Object صالح ورفض غير صالح.
- فشل متعمّد: namespace أو حالة حروف path خاطئة ثم شخّص class-not-found بدل إعادة تركيب المشروع عشوائيًا.
- محاولة مستقلة: أضف namespace مستقلًا و callback لا يغيّر مدخلاته خفية.
- دليل النجاح: إعادة تشغيل من README واختبارات types/errors وشرح capture والتحميل.

### 9.4 — DI وإعادة التنظيم بتغيير مبرر

- المستوى: أساسي إلزامي.
- المتطلبات: 9.2 و 9.3.
- الناتج: يقلل مسؤولية متضخمة مع الحفاظ على السلوك.

#### 9.4.a — مسؤولية واحدة واعتماد ظاهر

استخرج قرارًا تجاريًا من I/O، واستخدم constructor injection يدويًا. ناقش SOLID من مثال تغيير حقيقي لا اختبار حفظ أسماء؛ لا Container في domain.

#### 9.4.b — Refactoring و Patterns عند الحاجة

خطوات صغيرة واختبارات خضراء لكل خطوة. عالج duplication و god object؛ جرّب Strategy أو Adapter عند اختلاف سلوك فعلي. بقية Creational/Structural/Behavioral catalog اختياري ومربوط بمشكلة لاحقة.

**تطبيق وتقييم 9.4 بعد الأجزاء السابقة:**

- تجربة صغيرة: استبدل شرط provider طويلًا بعقد وتنفيذين مع نفس نواتج الاختبارات.
- فشل متعمّد: استخراج class يغيّر قاعدة رفض مستخدم؛ regression test يفشل.
- محاولة مستقلة: نظّم use case فيه حفظ وإشعار من غير تطبيق repository pattern آليًا.
- دليل النجاح: diff مفهوم واختبارات قبل وبعد وقرار يشرح تكلفة كل abstraction.

### 9.5 — اختبار السلوك وحدود الاعتماد

- المستوى: أساسي إلزامي.
- المتطلبات: 9.1–9.4 واختبارات المرحلة 3.
- الناتج: يثبت قاعدة عمل واختبار تكامل دون fake يخفي العطل.

#### 9.5.a — Unit و Integration و Test Doubles

اختبر outcome لا private methods. ميّز stub/fake/mock، ثم اجعل unit test صغيرًا و integration test على adapter فعلي؛ ثبّت clock/id source عند الحاجة.

#### 9.5.b — Static Analysis ومراجعة التصميم

شغّل أداة تحليل متوافقة على المختبر، وافصل خطأ type عن قاعدة عمل لا تراها الأداة. TDD تجربة اختيارية لتحسين feedback لا طقس إلزامي.

**تطبيق وتقييم 9.5 بعد الأجزاء السابقة:**

- تجربة صغيرة: use case يرسل إشعارًا واحدًا عند النجاح ولا يرسله عند الرفض.
- فشل متعمّد: fake يقبل payload لا يقبله adapter الحقيقي؛ اختبار التكامل يكشف الفرق.
- محاولة مستقلة: اكتب اختبارات مستقلة لحالة duplicate وعطل حفظ ومصدر وقت ثابت.
- دليل النجاح: نتائج tests وتحليل ساكن وتفسير ما لم تثبته الأدوات.

### 9.6 — مشروع إعادة تنظيم Task Manager

- المستوى: أساسي إلزامي.
- المتطلبات: 9.1–9.5.
- الناتج: يسلم Plain PHP منظمًا دون تغيير عقد المستخدم.

#### 9.6.a — تنفيذ Vertical Slice

اختَر إنشاء مهمة وإكمالها مع ملكيتها. اكتب acceptance tests أولًا، ثم domain/application/adapters بالحد الأدنى؛ لا تعيد كتابة المشروع كله.

#### 9.6.b — مراجعة وإصلاح مستقل

راجع coupling ومسار الأخطاء والأنواع وأسماء المسؤوليات. جهّز README ثم أعطِ الطالب عطلًا جديدًا: duplicate transition أو sender failure؛ هو يشخص ويصلح.

**تطبيق وتقييم 9.6 بعد الأجزاء السابقة:**

- تجربة صغيرة: تشغيل السيناريو نفسه قبل وبعد التنظيم والحصول على نفس العقد.
- فشل متعمّد: تغيير owner أو إرسال side effect قبل نجاح الحفظ؛ يجب أن يكشفه الاختبار.
- محاولة مستقلة: أضف cancel بقاعدة انتقال جديدة دون وصفة كاملة.
- دليل النجاح: README ورسم مسؤوليات واختبارات قبول ورفض وتغيير مستقل قابل للمراجعة.
