# المرحلة 11 — APIs وربط الواجهة

الإصدار: 1.1 — مراجعة المنهج 2026-10-21. مراجعة تحريرية؛ لم تبدأ الدراسة.

الـ API عقد بين عميل وخادم. هنصممه من استخدام حقيقي، ونختبر المدخلات والنتائج والفشل من عميلين، مش نحول كل جدول إلى endpoint وخلاص.

## المتطلبات وحدود المرحلة

نجاح مشروع Laravel المحلي 10 وأساس JavaScript/fetch في 7 و HTTP في 4؛ لا يشترط إكمال Laravel Query أو OOP القديمين كاملين.

تصميم العقد والملكية والحدود والاختبارات أساسي. Real-time و SSE/WebSocket تعميق اختياري بعد نجاح API عادية؛ فشل المتصفح أو إعادة الطلب يدخل correctness من البداية.

## خطة الدراسة

### 11.1 — Resource وعقد الطلب والاستجابة

- المستوى: أساسي إلزامي.
- المتطلبات: 10 و HTTP methods/status.
- الناتج: يكتب عقدًا يفهمه عميل مستقل ويحافظ على صلاحيات البيانات.

#### 11.1.a — Resource و HTTP Semantics

ابدأ بإنشاء حجز وقراءته وتحديثه. ميّز resource عن DB row وعن RPC action؛ اختر methods و status codes و safe/idempotent بالمعنى الفعلي، لا كل نتيجة 200.

#### 11.1.b — Validation و Representation وعقد الأخطاء

حدّد fields وأشكال IDs/وقت/أموال/null وفرق required عن missing. استخدم API Resource أو تحويل صريح؛ أخفِ الحقول الداخلية، وميّز 401/403/404/409/422 وفق سياسة موثقة.

**تطبيق وتقييم 11.1 بعد الأجزاء السابقة:**

- تجربة صغيرة: عميل curl يقرأ إنشاء حجز ويعرض validation error بعقد ثابت.
- فشل متعمّد: إرجاع password hash أو stack trace أو 200 لفشل؛ اختبار العقد يفشل.
- محاولة مستقلة: صمّم cancel endpoint ونتائجه دون نسخ حالة DB مباشرة.
- دليل النجاح: طلبات/استجابات فعلية وعقد errors واختبارات fields/ownership.

### 11.2 — قوائم بحدود وتغيير متوافق

- المستوى: أساسي إلزامي.
- المتطلبات: 11.1 و query bounds في 10.5.
- الناتج: يعرض قائمة قابلة للاستخدام دون استعلام غير محدود أو كسر عميل قديم.

#### 11.2.a — Pagination و Filter و Sort

اكتب allowed filters/sorts وحد page size وترتيبًا deterministic. قارن offset و cursor بمثال تغير البيانات؛ فرّق allowlist identifiers عن binding values.

#### 11.2.b — Compatibility و Versioning

ابدأ بتغيير إضافي ثم تغيير كاسر. حدّد contract deprecation ومتى تحتاج version؛ versioning مش حلًا لإهمال الاختبارات أو تغيير معنى field صامت.

**تطبيق وتقييم 11.2 بعد الأجزاء السابقة:**

- تجربة صغيرة: طلبات صفحتها محدودة وتصفية و sort يعيدان نتائج متوقعة.
- فشل متعمّد: limit ضخمة أو sort field داخلية أو زيادة بيانات تسبب duplicate pagination؛ رفض أو سلوك موثق.
- محاولة مستقلة: أضف filter محفوظ التوافق واختبار client قديم.
- دليل النجاح: اختبارات الحدود والترتيب وعدّ queries وعقد تغيير موثق.

### 11.3 — اختيار هوية العميل وحماية المتصفح

- المستوى: أساسي إلزامي.
- المتطلبات: 10.6 و cookies/sessions و same-origin.
- الناتج: يميّز session auth من token auth ويحمي كل عملية ومورد.

#### 11.3.a — Browser و API Clients

ارسم first-party browser و script خارجي. اختر session cookie أو personal token حسب المخاطر؛ تحقق من rotation/logout/revocation ومن أن CORS ليست authorization ولا JWT اختيارًا افتراضيًا.

#### 11.3.b — CORS و CSRF و Object Authorization

راقب credentials و preflight و trusted origins. اكتب matrix لزائر/مالك/مستخدم آخر/token محدود؛ token صالح لا يعني كل صلاحية.

**تطبيق وتقييم 11.3 بعد الأجزاء السابقة:**

- تجربة صغيرة: واجهة مأذون بها تستخدم API وتغيير ID لمورد آخر يُرفض.
- فشل متعمّد: origin غير مسموح أو طلب cookie بلا CSRF أو token بلا scope؛ لا تجاوز حماية.
- محاولة مستقلة: أضف endpoint تنزيل خاص باختيار auth ملائم للعميل.
- دليل النجاح: network trace بعد حجب secrets و tests لكل رفض وتبرير storage/transport لل credential.

### 11.4 — توثيق واختبار العقد وفشل العميل

- المستوى: أساسي إلزامي.
- المتطلبات: 11.1–11.3.
- الناتج: يشغل عميلين ويكتشف contract drift ويعالج timeout دون ادعاء فشل business operation.

#### 11.4.a — Schema و OpenAPI و Contract Tests

وثّق examples و required fields و errors و auth وحدود الطلبات ب schema قابلة للفحص مثل OpenAPI بإصدار متوافق. قارن implementation بالوثيقة ولا يكفي نجاح mock.

#### 11.4.b — Timeout و Cancel و Retry

ميّز إلغاء انتظار المتصفح عن إلغاء عملية على الخادم. ضع timeout ورسالة uncertain outcome و retry فقط بشرط الأمان؛ تفاصيل التكاملات في 17.

**تطبيق وتقييم 11.4 بعد الأجزاء السابقة:**

- تجربة صغيرة: curl و JavaScript يستعملان نفس العقد واختبار يرصد حذف field مطلوبة.
- فشل متعمّد: الخادم نفذ الحجز ثم ضاعت الاستجابة؛ العميل لا يقول إنه فشل باليقين.
- محاولة مستقلة: وثّق endpoint جديدًا وابنِ contract test يكشف نوعًا خاطئًا.
- دليل النجاح: schema و contract tests ولقطات مخرجات عميلين وحالة timeout مفسرة.

### 11.5 — نقل ملف واختيار Streaming عند الحاجة

- المستوى: أساسي إلزامي.
- المتطلبات: 11.3 وحدود uploads في 10.7.
- الناتج: ينقل ملفًا مأذونًابحد حجم ونوع واستهلاك ذاكرة مفهوم.

#### 11.5.a — Upload و Download و Streaming

افصل metadata عن المحتوى، وتحقق من الحجم والمحتوى والملكية ومكان التخزين. فسّر Content-Type/Disposition و stream response وحدود الذاكرة و client disconnect.

#### 11.5.b — SSE و WebSocket — امتداد اختياري

بعد الـ API العادية: قارن polling و SSE لاتجاه من الخادم ثم WebSocket للحوار ثنائي الاتجاه. ناقش auth/reconnect/ordering/backpressure؛ لا نطلب WebSocket لإكمال بوابة الأساس.

**تطبيق وتقييم 11.5 بعد الأجزاء السابقة:**

- تجربة صغيرة: تنزيل ملف تجريبي خاص مع قياس ذاكرة محدود ورفض مستخدم آخر.
- فشل متعمّد: ملف كبير أو مسار traversal أو انقطاع عميل؛ لا كشف ملفات ولا ملف تنفيذي عام.
- محاولة مستقلة: أضف download audit بلا مسار حساس؛ وإذا اختير real-time فسّر خطة reconnect.
- دليل النجاح: tests لل authorization والحدود وملاحظة ذاكرة؛ توثق حالة امتداد real-time إن لم يدرس.

### 11.6 — واجهة تتعامل مع حالة الطلب

- المستوى: أساسي إلزامي.
- المتطلبات: 11.1–11.4 و JS DOM/async.
- الناتج: تعرض loading/error/empty/success دون فقد تعديل المستخدم.

#### 11.6.a — State وتمثيل الحالات

ارسم state transitions ثم DOM update. ميّز خطأ شبكة من HTTP error ومن validation؛ request متأخرة لا ينبغي أن تستبدل نتيجة أحدث.

#### 11.6.b — Retry و Accessibility وحفظ المسودة

عطّل زر الإرسال لتحسين UX لا ضمان exactly-once. قدّم feedback قابلًا للقراءة بالكيبورد وقارئ الشاشة، واحفظ المدخل عند الرفض؛ إعادة الإرسال مرتبطة بـ 11.7.

**تطبيق وتقييم 11.6 بعد الأجزاء السابقة:**

- تجربة صغيرة: واجهة حجوزات بحالات واضحة وتأخر مصطنع لطلبين لا يغيّر الحالة خطأ.
- فشل متعمّد: timeout أو 422 أو response قديمة؛ النص لا يضيع ولا success وهمية.
- محاولة مستقلة: أضف filter وتعديلًا مع منع stale response بدون نسخ الحل.
- دليل النجاح: browser test أو سيناريو يدوي قابل للتكرار واختبارات حالات state.

### 11.7 — التكرار والتعديل المتزامن في API

- المستوى: أساسي إلزامي.
- المتطلبات: 11.1–11.6 و transaction و unique constraint الأساسية.
- الناتج: يمنع إنشاء مكررًا و lost update بسياسة صريحة يمكن شرح حدودها.

#### 11.7.a — Business Idempotency

حدّد scope و payload hash ونتيجة التكرار ومدة الاحتفاظ. استخدم DB constraint و transaction في مختبر واحد؛ HTTP idempotent method لا يعني أن POST payment آمنة للتكرار.

#### 11.7.b — Optimistic Concurrency و Conditional Requests

تتبع عميلين قرآ نسخة واحدة. اختر version field أو ETag/If-Match بعقد محدد، وارفض stale update بدل last-write-wins الصامت؛ HTTP caching أشمل في 4.

**تطبيق وتقييم 11.7 بعد الأجزاء السابقة:**

- تجربة صغيرة: إعادة نفس الطلب بنفس المفتاح تنتج حجزًا واحدًا، وتعديل نسخة قديمة يُرفض.
- فشل متعمّد: نفس المفتاح بـ payload مختلف أو عميلان يحاولان تعديل حقل واحد؛ لا overwrite صامت.
- محاولة مستقلة: صمّم عقد 409/412 أو version conflict وواجهة تعرض الحل الممكن.
- دليل النجاح: اختبار duplicate وتزامن حقيقي بعميلين وتوثيق حدود المختبر؛ عمق الـ locks في 14.

## المشروع وبوابة الخروج

واجهة JavaScript وعميل curl لنفس Laravel API: pagination وحدود وعقد أخطاء وصلاحيات وتوثيق ومنع duplicate/lost update. القبول بتشغيل نفس acceptance من العميلين، وكشف تغيير يكسر العقد، وعدم فقد المدخل عند 422/timeout. SSE/WebSocket اختياريان ولا يعطلان العبور.

## مراجع وحدود الربط

استند إلى HTTP في 4 وملكية البيانات في 10؛ مراجع Laravel الرسمية لـ API Resources/Sanctum/testing حسب الإصدار، ومرجع OpenAPI الرسمي المناسب لنسخة schema. [AUTHENTICATION_AUTHORIZATION_MASTER_PROMPT.md](../AUTHENTICATION_AUTHORIZATION_MASTER_PROMPT.md) Modules 2–5 للتعميق في session/token والتهديدات، لا شرط إنهاء Module 13 قبل بناء API. التفويض الموزع و webhook delivery في 12 و 17 حسب المتطلبات.

## تشغيل الجلسة والتقدم

اقرأ README.md و COMMON_RULES.md وهذا الملف وملف PROGRESS المجاور كاملين. اشرح بالعامية المصرية الطبيعية: المشكلة ثم الفكرة وآليتها ثم تجربة صغيرة وتوقع الناتج قبل التنفيذ. مفهوم واحد وسؤال واحد كل مرة؛ لا تعرض حل المحاولة المستقلة قبل محاولة الطالب. كل عنوان فرعي وحدة شرح، وليس درسًا موسوعيًا في رسالة واحدة.

الـ IDs المحلية تقيس أدلة هذا المنهج فقط. ملفات study القديمة مراجع وتعميق وليست شرط إتمام كامل قبل العبور. لا تنسخ درجاتها، ولا تعتبر نجاح بوابة محلية نجاحًا تلقائيًا في نقطة قديمة. إن اختار الطالب دراسة المالك كاملًا، اقرأ منهجه وتقدمه والتزم بترتيبه؛ سجل الربط دون ازدواج النتائج.

حدّث التقدم المحلي وفق الدليل الحقيقي: checkpoint والعنوان الفرعي وآخر تمرين مكتمل والخطوة غير المكتملة والاختبارات والفجوات. شرط النجاح 80% على الأقل مع أدلة مستقلة وإصلاح أخطاء الأمان أو صحة البيانات الجوهرية. المتقدم الاختياري لا يعطل بوابة الأساس، ولا يسجل Passed أو درجة وهمية إن لم يُدرس. لا نشر أو commit أو push أو تعديل لتقدم مسار قديم تلقائيًا.
