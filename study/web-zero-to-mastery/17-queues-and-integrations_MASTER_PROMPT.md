# المرحلة 17 — Queues والتكاملات الموثوقة

الإصدار: 1.1 — 2026-10-21. التخصص: Backend متقدم، وكل checkpoint أدناه أساسي لبوابة هذه المرحلة؛ مقارنات المنتجات امتداد اختياري.

المتطلبات: بوابة 16، و transactions من 14، و API contracts من 11. نراجع process/signal من 13؛ تجهيز Docker/Compose البسيط من 16 يكفي إن اختير، ولا نحتاج إنهاء 18 لبدء المختبر. يمكن تشغيل worker محليًا بلا حاويات. اختبار الدخول: عملية تجارية داخل transaction ونداء HTTP بمهلة محدودة، مع تفسير الفرق بين فشل الرد وفشل الأثر.

## مسار الشرح: من شغل محلي إلى تكامل يتحمل الفشل

### 17.1 — لماذا Queue وكيف نشغّلها؟

#### 17.1.a — Job و Message و Event

- المتطلب والهدف: API contract؛ يحدد الطالب مين producer ومين consumer وإيه اللي بيرجع للمستخدم قبل انتهاء الشغل.
- الشرح: مشكلة إرسال تقرير بطيء ← synchronous مقابل async ← broker و queue مقابل log؛ Laravel queue أولًا، ومقارنة RabbitMQ/Kafka عند اختلاف متطلبات ordering/replay، لا حفظ أسماء.
- المختبر والنتيجة المتوقعة: dispatch لتقرير إلى connection تجريبية ثم تشغيل worker؛ الطلب يعيد معرف متابعة، والتقرير يصبح جاهزًا بعد المعالجة.
- الفشل ودليل النجاح: أوقف worker؛ يجب أن يظل job قابلًا للملاحظة لا «نجاحًا» وهميًا. الطالب يثبت موضع الشغل والـ source of truth قبل وبعد المعالجة.

#### 17.1.b — إعداد Worker و Payload قابلة لإعادة المحاولة

- المتطلب والهدف: 17.1.a؛ يفرق بين connection و queue وبين sync driver و worker حقيقي، ويفسر serialization ومخاطر model تغير بعد dispatch.
- الشرح: إعداد driver المدعوم في نسخة المختبر ← job يحمل IDs وبيانات محددة لا secrets بلا حاجة ← تحميل الحالة عند التنفيذ ← تشغيل/إيقاف/restart العامل عند الإصدار.
- المختبر والنتيجة المتوقعة: عاملان و job يحمل record ID؛ عدّل السجل قبل المعالجة، ثم وضح هل العقد يستخدم snapshot ولا أحدث حالة، وتحقق من السلوك.
- الفشل ودليل النجاح: مرر record محذوفًا أو payload غير صالحة؛ يجب أن تظهر سياسة فشل واضحة. الدليل: إعداد منقح، commands، سجل محاولات، وتوقع مستقل قبل التنفيذ.

### 17.2 — Delivery و Idempotency

#### 17.2.a — Ack و Timeout وحدود الضمان

- المتطلب والهدف: 17.1؛ يتتبع الطالب job من reservation إلى ack، ويميز at-most/at-least-once دون ادعاء exactly-once لكل النظام.
- الشرح: مدة التنفيذ ← worker timeout ← retry/visibility حسب driver؛ اضبطها وفق وثائق النسخة الفعلية، ولا تخلط اسم إعداد Laravel بضمان كل broker.
- المختبر والنتيجة المتوقعة: job بطيء وعاملان؛ اجعل timeout/مهلة إعادة الإتاحة غير متوافقتين في بيانات تجريبية، ثم أصلحهما وراقب المحاولات.
- الفشل ودليل النجاح: قتل العامل قبل ack قد يعيد المحاولة؛ يفسر الطالب السبب ويثبت أن ضبط التوقيت لا يغني عن idempotency، مع timeline حقيقي.

#### 17.2.b — أثر تجاري واحد رغم التكرار

- المتطلب والهدف: 17.2.a و unique constraints/transactions؛ يبني consumer يحمي business operation ID، لا يكتفي بعلم boolean في الذاكرة.
- الشرح: duplicate/out-of-order ← deduplication boundary و retention ← transaction مع سجل النتيجة؛ unique job أو منع overlap وسائل تشغيلية وليست بديلًا عن العقد التجاري.
- المختبر والنتيجة المتوقعة: نفس event ثلاث مرات ومن عاملين؛ عدد المحاولات قد يزيد، لكن قيد العمل والنتيجة لا يتكرران.
- الفشل ودليل النجاح: crash بعد تنفيذ الأثر وقبل ack، ثم إعادة إرسال؛ يثبت الطالب بالأرقام والاختبارات عدم الخصم/الحجز المزدوج، ويشرح حد الضمان عند مزود خارجي.

### 17.3 — Retry و Backpressure

#### 17.3.a — إعادة محاولة محدودة و DLQ

- المتطلب والهدف: 17.2؛ يميز transient failure من permanent failure، ويختار attempts و deadline و backoff/jitter من الحاجة.
- الشرح: timeout/429/validation failure ← سياسة retry ← poison message و DLQ ← replay مأذون بعد الإصلاح؛ لا retry أبدية ولا replay جماعي بلا rate limit.
- المختبر والنتيجة المتوقعة: provider fake يفشل مرتين ثم ينجح، وآخر يرفض البيانات دائمًا؛ الأول يتعافى والثاني يعزل مع سبب قابل للفحص.
- الفشل ودليل النجاح: retry storm مصغرة؛ يضبط الطالب السياسة، ويقارن عدد المحاولات والتأخير قبل الإصلاح وبعده.

#### 17.3.b — حمل أكثر من قدرة Workers

- المتطلب والهدف: 17.3.a؛ يفسر backlog و consumer lag ويحدد حد التزامن والقبول بدل زيادة workers بلا سقف.
- الشرح: arrival/service rate ← queue age/عمقها ← backpressure و priority/fairness ← graceful shutdown وحدود الذاكرة وعمر العامل.
- المختبر والنتيجة المتوقعة: حمل محدود يتجاوز قدرة مزود وهمي؛ تظهر queue age، ويظل المزود دون حصته ويستكمل العامل الشغل أو يسلمه لإعادة آمنة.
- الفشل ودليل النجاح: shutdown أثناء job مع backlog؛ الدليل drain/retry قابل للملاحظة، وعدم اختفاء jobs، وتفسير تكلفة زيادة concurrency.

### 17.4 — Transaction Boundary و Event Contract

#### 17.4.a — After Commit و Outbox/Inbox

- المتطلب والهدف: 17.2 و transactions؛ يحدد الطالب dual-write gap، ويفرق تأجيل dispatch لما بعد commit عن حل فقد الرسالة عند crash.
- الشرح: job قبل commit قد يقرأ بيانات غير موجودة ← after-commit لسيطرة التوقيت ← outbox داخل نفس transaction و publisher قابل لإعادة المحاولة ← inbox عند الاستقبال.
- المختبر والنتيجة المتوقعة: transaction تُلغى ثم أخرى تنجح؛ الأولى لا تحدث أثرًا خارجيًا، والثانية تبقى مسجلة لإرسالها حتى لو مات publisher.
- الفشل ودليل النجاح: crash بعد commit وقبل publish؛ يستعيد الطالب الحدث من outbox ويثبت مسار duplicate الآمن، دون وصف after-commit كضمان durable وحده.

#### 17.4.b — Schema Evolution بلا كسر المستهلك

- المتطلب والهدف: 17.4.a؛ يكتب event ID/type/version/time/payload ويحدد fields الإلزامية والتوافق.
- الشرح: schema validation ← إضافة حقل متوافق ← event version عند تغيير معنى ← quarantine لعقد غير مدعوم؛ ترتيب التسليم مش ترتيبًا تجاريًا مضمونًا.
- المختبر والنتيجة المتوقعة: fixtures للإصدارين القديم والجديد ومستهلك يتعامل معهما وفق العقد؛ السلوك موثق وقابل للاختبار.
- الفشل ودليل النجاح: إصدار غير معروف أو حقل ناقص؛ لا تعديل تجاري صامت. الدليل اختبارات contract وإجراء ترقية تدريجي يشرحه الطالب.

### 17.5 — External APIs تحت الفشل الجزئي

#### 17.5.a — Timeout Budget و Containment

- المتطلب والهدف: 17.3 و HTTP؛ يوزع مهلة محدودة، ويفرق quotas من concurrency، ويعرف متى يحتاج circuit breaker أو bulkhead.
- الشرح: dependency بطيء ← connection/read/overall timeouts ← retry داخل budget ← circuit state/fallback مقيد؛ fallback لا يخترع نجاح دفع أو حجز.
- المختبر والنتيجة المتوقعة: مزود بطيء وآخر سليم؛ يظل الثاني قابلًا للاستخدام وتظهر نتيجة pending/failure مفهومة للأول.
- الفشل ودليل النجاح: بطء متزامن و 429؛ يثبت الطالب bounded attempts والموارد، ويبرر سياسة تعطيل المزود والتعافي.

#### 17.5.b — Unknown Outcome ومصالحة النتيجة

- المتطلب والهدف: 17.5.a و 17.2.b؛ يميز «مش عارف النتيجة» من«العملية فشلت»، ويتجنب تكرار أثر خارجي غير قابل للإلغاء.
- الشرح: request ID/idempotency key حسب عقد المزود ← response lost بعد الأثر ← status query/reconciliation ← audit trail؛ تعويض عند لزومه وليس rollback سحريًا.
- المختبر والنتيجة المتوقعة: المزود ينفذ ثم يقطع الرد؛ يحتفظ النظام بحالة مجهولة ويصل للنتيجة بمصالحة موثقة.
- الفشل ودليل النجاح: provider لا يدعم dedup ولا status query؛ يذكر الطالب صراحة حد الضمان وإجراء المراجعة، ولا يعد بعملية واحدة لا يمكن إثباتها.

### 17.6 — Webhooks موثوقة وآمنة

#### 17.6.a — قبول الحدث والتحقق من صاحبه

- المتطلب والهدف: 12 و 17.4؛ يحقق signing على bytes الفعلية وفق عقد المزود، مع timestamp/key ID/replay window حيث يدعم العقد.
- الشرح: TLS لا يثبت أن event من المزود ← signature/secret rotation ← limits و validation ← حفظ durable ثم ack؛ لا logging للأسرار.
- المختبر والنتيجة المتوقعة: حدث صحيح، signature خاطئة، replay، timestamp قديم؛ القبول والرفض يطابقان سياسة معلنة.
- الفشل ودليل النجاح: عدّل body بعد توقيعه؛ لا أثر تجاري. الدليل test fixtures وسجل منقح يشرح سبب الرفض دون كشف secret.

#### 17.6.b — Ordering و Reconciliation و Audit

- المتطلب والهدف: 17.6.a؛ يحمي انتقالات الحالة من event قديم ويحدد event log/history دون جعله مصدر الحقيقة تلقائيًا.
- الشرح: duplicate/version/ordering ← state transition invariant ← delayed delivery ← reconciliation job وإعادة الإرسال مع audit.
- المختبر والنتيجة المتوقعة: delivered ثم pending قديم ثم duplicate؛ الحالة لا ترجع للخلف بلا مبرر، وتظل كل محاولة قابلة للتتبع.
- الفشل ودليل النجاح: حدث مفقود؛ تكتشفه المصالحة وتصحح الحالة بدليل لا بتعديل يدوي صامت. الطالب يضيف حالة فشل مستقلة.

### 17.7 — إثبات الضمانات بالتجربة

#### 17.7.a — Fake و Contract واختبار تكامل حقيقي

- المتطلب والهدف: 17.1–17.6؛ يعرف ما تثبته unit/fake tests وما يحتاج worker/DB فعليين؛ provider fake ليس إثباتًا لتوافق API الحقيقي.
- الشرح: fixture contract ← اختبار consumer ← worker حقيقي مع DB تجريبية ← sandbox مأذون اختياري للمزود؛ لا بيانات عملاء أو مدفوعات حقيقية.
- المختبر والنتيجة المتوقعة: fake يختبر retry، وتكامل محلي يختبر commit/ack؛ يستطيع الطالب ربط كل assertion بالضمان الذي يختبره.
- الفشل ودليل النجاح: fixture مخالفة للعقد؛ يجب أن يفشل الاختبار بدل fake يمرر أي payload. الدليل تشغيل مستقل قابل للتكرار.

#### 17.7.b — Failure Matrix وإغلاق المشروع

- المتطلب والهدف: 17.7.a؛ يبني Integration Hub بمزودين وهميين، استقبال وإرسال ومصالحة، ثم يثبت حدوده.
- الشرح: اكتب expected state و business invariant قبل fault، شغّل الحالة، قارن النتيجة وسجل recovery/remaining risk.
- المختبر والنتيجة المتوقعة: matrix إلزامية: duplicate، reorder، timeout قبل الأثر، قطع الرد بعد الأثر، crash قبل commit، crash بعد commit وقبل publish، قتل worker قبل ack، و DLQ/replay.
- الفشل ودليل النجاح: مفاجأة يختارها المقيّم بلا وصفة؛ لا يكرر الأثر التجاري ولا يخفي فقده، أو يسجل unknown outcome بصدق حين يمنع عقد المزود ضمانًا أقوى. الأدلة: tests، counters، timeline، وعرض دفاعي.

## بوابة المرحلة والمراجع

كل checkpoint له تقييم محلي وفق COMMON_RULES؛ لا يُغلق إلا باستكمال sublessons الأساسية ودليلها. المشروع هو 17.7.b؛ الدرجة لا تعوض تسريب secret أو تكرار أثر تجاري خطير. تُراجع queue configuration حسب إصدار المختبر في [Laravel Queues](https://laravel.com/docs/queues). التوسع المقارن في [System Design](../SYSTEM_DESIGN_MASTER_PROMPT.md)، العناوين `Module 10 — Messaging وEvent-Driven Architecture` و`Module 11 — APIs وService Communication` و`Module 12 — Reliability وResilience` مرجع، لا شرط إكمال المنهج القديم ولا درجات منسوخة.

## تشغيل جلسة هذه الجزئية

- اقرأ [الفهرس](README.md) و[قواعد التدريس والتقييم](COMMON_RULES.md) كاملين، ثم هذا الملف و[ملف التقدم](17-queues-and-integrations_PROGRESS.md) كاملين قبل الشرح.
- هذا الملف منهج الجزئية، وليس الدرس المنشور أو دليل اجتيازها. اشرح checkpoint واحدة على أجزاء، وسؤالًا واحدًا كل مرة، بالعامية المصرية و PHP افتراضيًا إلا في موضوع لغة أخرى.
- ملف التقدم المجاور يملك الموضع والنتائج الخاصة بهذه الجزئية. الفهرس وملف التوجيه العام لا يكرران الدرجات.
- المسارات القديمة مراجع للتعمق، لا يُفرض إكمالها لإغلاق البوابة المحلية. لو اختار الطالب دراسة مسار قديم مستقلًا اقرأ Master و Progress الخاصين به، واحفظ درجاته هناك دون نسخها هنا.
- قواعد المنهج المشتركة وخرائط ملاك الموضوعات في COMMON_RULES.md؛ أسماء ملفات المسارات القديمة المذكورة أعلاه تُحل من study الأب، لا من هذا المجلد.

## إنهاء الجلسة

حدّث تقدم الويب المحلي وفق دليله فقط. لا تعدّل تقدم مسار قديم إلا إذا اختار الطالب دراسة ذلك المسار مستقلًا واتُّبعت قواعده؛ الاستعانة بمرجع لا تمنح نجاحًا فيه. حدّث مؤشر العودة عند تغيير الجزئية، ولا تبدأ التالية تلقائيًا أو تسجل Passed بسبب إنشاء الملفات. لا نشر أو commit أو push تلقائي.
