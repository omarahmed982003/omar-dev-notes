أنت بتبعت ملف أو طلب لخادم. الطريق ممكن يضيّع جزء من البيانات، أو يوصل جزء متأخر، أو يكرر بيانات. برنامجك محتاج يشوف البايتات بالترتيب اللي اتبعتت بيه، ويعرف إن الاتصال فشل لو النقل ما قدرش يكمل. دي المشكلة اللي TCP بيحلها.

محتاج تعرف **IP**: قواعد عنونة وتوجيه Packets، وهي وحدات بيانات بتتحرك بين الأجهزة. و**Port**: رقم بيساعد Operating System يحدد نقطة استقبال البيانات داخل الجهاز. **DNS** نظام بنسأله عن معلومات اسم الموقع، ومنها عنوان IP؛ TCP نفسه ممكن يتصل بعنوان مباشر من غير بحث DNS.

**مسار القراءة:** أول مرور لحد «توقف التأسيس» تحت. تفاصيل الاستعادة والازدحام والتشخيص جاية بعده في نفس الصفحة؛ مش دروس تكملة منفصلة.

## TCP بيقدم إيه لبرنامجك؟

**Transmission Control Protocol** بروتوكول نقل بيقدم **Byte stream**: تدفق بايتات مرتب بين طرفين. البايت وحدة من 8 بتات. TCP بيرتب البيانات ويعالج الفقد والتكرار داخل الاتصال، لكنه مش بيحافظ على حدود رسائل التطبيق.

لو أرسلت النصين `Hello` و`World` في استدعاءين، المستقبل ممكن يقرأ `HelloWorld` مرة واحدة، أو يقرأ أجزاء أصغر. عدد مرات الكتابة مش لازم يساوي عدد مرات القراءة. التطبيق هو اللي يحدد نهاية الرسالة، مثلًا بنهاية سطر أو بطول مكتوب قبل المحتوى.

الاعتمادية هنا مش وعد إن الشبكة عمرها ما هتقع. فيه مهلات وحدود وموارد؛ لو ما قدرش يكمل، الاتصال ممكن يفشل. وكلمة «اتصال» مش معناها إن فيه سلك محجوز ليك على طول الطريق؛ الطرفان بيحتفظوا بحالة مشتركة للنقل.

## مين متصل بمين؟

في حالة TCP المعتادة، الاتصال بيتحدد بعنوان ومنفذ كل طرف:

```text
Client 127.0.0.1:51024  <-->  Server 127.0.0.1:9099
```

عنوان `127.0.0.1` بيرجع لنفس الجهاز. العميل عادة بياخد منفذًا مؤقتًا من النظام، وserver بيستنى على منفذ معروف. عميل تاني يقدر يكلم نفس server بمنفذ مصدر مختلف. الأرقام هنا مثال؛ المنفذ المؤقت الفعلي ممكن يختلف.

**Socket** هي واجهة بيستخدمها البرنامج للتواصل مع طبقة الشبكة. server بيعمل **Listen**، يعني يستعد لقبول اتصالات، وبعدها **Accept** يرجع له موردًا يمثل اتصالًا مقبولًا. ده مختلف عن رسالة التطبيق اللي هتتبعت بعد كده.

## الاتصال بيبدأ إزاي؟

في البداية المعتادة بتحصل مصافحة ثلاثية، **Three-way handshake**:



**SYN** بيبدأ مزامنة أرقام التتابع. **ACK** بيأكد التقدم المتوقع من الطرف الآخر. كل اتجاه له أرقام تتابع مستقلة؛ الطرفان مش بيتشاركوا عداد بايتات واحد. SYN نفسه بيستهلك رقمًا في مساحة التتابع، علشان كده التأكيد في الرسم زاد واحدًا.

نجاح المصافحة معناه إن نقطة TCP قبلت الاتصال. لسه ما يثبتش إن المستخدم مسموح له يدخل أو إن قاعدة البيانات شغالة. المصادقة ومنطق التطبيق بييجوا فوق النقل.

## الاتصال بينتهي إزاي؟

كل اتجاه يقدر ينتهي لوحده. **FIN** معناه «مش هبعت بيانات جديدة في الاتجاه ده». الطرف التاني يؤكد FIN، ولسه ممكن يبعت بياناته الباقية. الإغلاق المعتاد بيتضمن FIN و ACK لكل اتجاه، وممكن بعض الرسائل تندمج؛ مش لازم تشوف أربع حزم منفصلة دائمًا.

**Half-close** يعني إنهاء الإرسال مع استمرار الاستقبال. أما **RST** فيعيد ضبط الاتصال بصورة مفاجئة بدل الإغلاق المنظم. برنامجك لازم يتعامل مع **EOF — نهاية التدفق** أو خطأ، ومش يفترض إن كل انتهاء يعني اكتمال الرسالة المطلوبة.

## تجربة محلية بـ PHP: رسالتك مش هي اتصالك

التشغيل اختياري بعد [تجهيز PHP](/php/00-lab-setup/)، و**CLI — واجهة سطر الأوامر** لتشغيل الملف من الطرفية. من غير تشغيل، تتبع المدخل Hello مع نهاية سطر: server يقبل الاتصال ثم يقرأ رسالة محددة الإطار ويرد Received: Hello. قبول الاتصال ليس رد التطبيق. لو اخترت التنفيذ، هتشغّل ملف خادم وملف عميل في طرفيتين. افتح مجلد تدريب فاضي على جهازك، واستعمل منفذ `9099` محليًا؛ مش محتاج تفتح المنفذ للإنترنت.

احفظ الملف باسم `tcp-server.php`:

```php
<?php
declare(strict_types=1);

$server = stream_socket_server('tcp://127.0.0.1:9099', $code, $message);
if ($server === false) {
    throw new RuntimeException($message, $code);
}
echo 'Listening', PHP_EOL;
$client = stream_socket_accept($server, 15);
if ($client === false) {
    fclose($server);
    throw new RuntimeException('No client connected');
}
stream_set_timeout($client, 5);
$line = fgets($client, 128);
if ($line !== "Hello\n") {
    fclose($client);
    fclose($server);
    throw new RuntimeException('Expected one short newline-terminated message');
}
$response = "Received: Hello\n";
while ($response !== '') {
    $written = fwrite($client, $response);
    if ($written === false || $written === 0) {
        throw new RuntimeException('Write failed');
    }
    $response = substr($response, $written);
}
fclose($client);
fclose($server);
```

شغّل server:

```bash
php tcp-server.php
```

هيظهر `Listening` ويستنى عميلًا لحد 15 ثانية. بعد قبول العميل، القراءة لها مهلة 5 ثوانٍ. احفظ الملف التاني باسم `tcp-client.php` وشغّله من طرفية تانية أثناء الانتظار:

```php
<?php
declare(strict_types=1);

$socket = stream_socket_client('tcp://127.0.0.1:9099', $code, $message, 5);
if ($socket === false) {
    throw new RuntimeException($message, $code);
}
stream_set_timeout($socket, 5);
$request = "Hello\n";
while ($request !== '') {
    $written = fwrite($socket, $request);
    if ($written === false || $written === 0) {
        throw new RuntimeException('Write failed');
    }
    $request = substr($request, $written);
}
$response = fgets($socket, 128);
fclose($socket);
if ($response !== "Received: Hello\n") {
    throw new RuntimeException('Missing or incomplete response');
}
echo $response;
```

```bash
php tcp-client.php
```

الناتج المتوقع عند العميل:

```text
Received: Hello
```

`fgets` هنا بتقرأ لحد نهاية سطر أو حد القراءة أو انتهاء المورد. اخترنا نهاية السطر علشان تحدد **رسالة التطبيق**. حلقات `fwrite` موجودة لأن الكتابة قد تقبل عدد بايتات أقل من المطلوب؛ لازم نكمّل الباقي. المثال بيرفض رسالة طويلة أو ناقصة؛ مش بروتوكول إنتاج يقبل أي حجم.

server يقبل عميلًا واحدًا ثم ينتهي. العميل يبدأ اتصال TCP، وبعده يرسل الرسالة، وبعده يستقبل رد التطبيق. فرق بين نجاح الاتصال وبين تطابق الرد المتوقع. المثال مشفرش البيانات؛ على شبكة غير محلية محتاج تصميم حماية مناسب.

## TCP وصل البيانات، هل الطلب اتنفذ؟

**TCP ACK** يثبت تقدم النقل، مش حفظ الطلب في قاعدة البيانات. وممكن server ينفذ دفعًا، وبعدها ينقطع الاتصال قبل ما العميل يستلم الرد. العميل مش هيعرف من انقطاع الاتصال وحده هل الدفع حصل.

إعادة نفس الطلب ممكن تعمل أثرًا تجاريًا تاني. **Idempotency** سياسة تطبيق تمنع تضاعف الأثر المقصود عند إعادة نفس العملية، مثل مفتاح طلب فريد ونتيجة محفوظة. TCP يعالج تكرار بايتات داخل الاتصال؛ التطبيق مسؤول عن تكرار طلبات كاملة عبر اتصالات مختلفة.

## توقف التأسيس: اتصال ورسالة ونتيجة

دلوقتي المطلوب تفسر المصافحة، وتفرّق بين الاتصال ورسالة التطبيق، وتوضح ليه الكتابة والقراءة قد تكونان جزئيتين. وتتوقع FIN المنظم مقابل RST المفاجئ، وتعرف إن ACK لا يثبت تنفيذ دفع.

لو عرفت تتبع Hello والرد من غير افتراض حدود رسائل داخل TCP، كمل مسار الأساس. الأقسام التالية تعمق مرتب: أرقام البايتات، ثم الحجم، ثم نافذتا المستقبل والطريق، ثم تفاصيل الإغلاق والتشخيص. ارجع لها بعد أول تطبيق ويب محلي.

## ترتيب البايتات وتأكيد وصولها

تخيل نطاق بيانات يبدأ عند الرقم 1000، وفيه `ABCDEF`. أول ثلاثة بايتات هي 1000 و 1001 و 1002، والثلاثة اللي بعدهم تبدأ عند 1003. رقم التتابع بيحدد موضع البايت، مش «رقم الحزمة الرابعة» ولا «رقم طلب الشراء».

**Cumulative ACK** المعتاد بيشير لرقم البايت التالي المتوقع: تأكيد 1003 معناه إن البايتات السابقة وصلِت بترتيب متصل. لو جزء ناقص وفيه بيانات بعده، TCP ممكن يحتفظ باللي وصل ويستعيد الناقص، وبعدها يسلّم للتطبيق تدفقًا مرتبًا.

```text
وصل:       ABC     [جزء ناقص]     GHI
للتطبيق:   ABC
بعد التعويض: ABCDEF GHI بالترتيب
```

**Retransmission** معناها إعادة إرسال بيانات استُنتج إنها ضاعت، اعتمادًا على المؤقتات ومعلومات التأكيد. استنتاج الفقد ممكن يكون غلط بسبب تأخير أو إعادة ترتيب؛ التنفيذ بيتعامل مع الاحتمالات دي. آليات زي **SACK** تسمح للطرف المستقبل يبلغ عن نطاقات إضافية وصلت، فتساعد المرسل يعرف الفجوات.

لو بيانات جديدة وصلت لكن فيه فجوة قبلها، التطبيق ممكن يستنى سد الفجوة. ده اسمه **Head-of-line blocking** في تدفق TCP: البيانات موجودة لكن مش جاهزة للتسليم المرتب.

### تتبع فقد بأرقام فعلية

نفس بداية المثال: نريد إرسال ABC ثم DEF ثم GHI، كل مجموعة 3 بايتات. نفترض مستقبلًا يحتفظ بما وصله خارج الترتيب، ونختار نقاط إظهار ACK للتعليم؛ مش قاعدة أن كل مقطع له ACK منفصلة فورًا.

| الحدث | بايتات البيانات | رد المستقبل في التتبع | المتاح للتطبيق حتى الآن |
|---|---|---|---|
| تصل ABC |1000–1002| ACK 1003 |ABC|
| تضيع DEF في الطريق |1003–1005| لا يراها المستقبل |ABC|
| تصل GHI قبل الناقص |1006–1008| ACK 1003: ما زلت أحتاج البايت 1003 |ABC؛ يحتفظ بـ GHI داخليًا |
| يعيد المرسل DEF فتصل |1003–1005| ACK 1009: النطاق حتى 1008 أصبح متصلًا |ABCDEFGHI|

ACK 1003 لا يعني أن المستقبل لم ير أي بايت أعلى منه؛ معناه أن **الجزء المتصل** يقف قبل 1003. لما تسد DEF الفجوة، يقدر يؤكد 1009 لأن GHI موجودة بالفعل.

نفترض هنا أن المرسل قرر الإعادة بعد مهلة مناسبة. **ACK مكررة واحدة لا تفرض وحدها قرار إعادة فوريًا**. مؤقتات الاستعادة وخوارزمياتها تختلف؛ المثال يشرح النتيجة والترتيب، لا يحاكي كل تنفيذ TCP.

**تدريب مستقل:** البداية 2000. تصل JKL، وتضيع MNO، ثم تصل PQR. كل مجموعة 3 بايتات. ما ACK بعد وصول PQR؟ وما ACK بعد تعويض MNO؟

JKL هي 2000–2002؛ الفجوة تبدأ 2003، لذلك ACK 2003 رغم وصول 2006–2008. بعد التعويض يصبح النطاق حتى 2008 متصلًا فتكون ACK 2009. التطبيق لا يستلم PQR قبل الفجوة وفق تدفق TCP المرتب.

## حجم الجزء بيتحدد إزاي؟

بيانات التطبيق بتنزل لطبقات النقل، بعدها IP، بعدها الوصلة المحلية:

```text
Application bytes → TCP segment → IP packet → Ethernet/Wi-Fi frame
```

كل طبقة بتضيف **Header**: معلومات علشان الطرف المقابل يعرف يتعامل مع الوحدة. TCP فيه المنافذ وأرقام التتابع والأعلام؛ IP فيه العناوين ومعلومات التوجيه. عنوان MAC يخص الوصلة المحلية، والراوتر يختار الخطوة التالية لحزمة IP.

**MTU** أقصى حجم حمولة طبقة أعلى تقدر الوصلة تحملها. **MSS** أقصى مقدار بيانات TCP يعلن الطرف إنه مستعد يستقبله في مقطع، باستثناء رؤوس TCP و IP. MSS و MTU مش نفس الرقم، ومعلومات المسار والخيارات بتأثر على التقسيم الفعلي. نقل رسالة كبيرة مش معناه إرسال حزمة واحدة بنفس حجمها.

**Path MTU Discovery** بيحاول يحدد الحجم المناسب للمسار. لو رسائل التحكم المرتبطة بالحجم اتحجبت، ممكن اتصال صغير ينجح ونقل بيانات أكبر يتعطل. ده احتمال تشخيصي، مش حكم تلقائي على كل رفع ملف فاشل.

قيمة **Checksum** بتساعد تكشف فسادًا عرضيًا في البيانات، لكنها مش حماية ضد مهاجم يزوّر بيانات. TCP لوحده مش تشفير؛ حماية محتوى الاتصال تحتاج بروتوكولًا زي TLS.

## نافذة المستقبل وازدحام الشبكة

فيه مشكلتان مختلفتان:

- المستقبل ممكن يكون أبطأ من المرسل. **Flow control** يستخدم نافذة الاستقبال المعلنة، `rwnd`، علشان ما يغرقش المستقبل.
- الطريق نفسه ممكن يكون مزدحمًا. **Congestion control** يضبط كمية البيانات الموجودة في الطريق بنافذة ازدحام عند المرسل، `cwnd`.

الكمية المسموح بوجودها من غير تأكيد بتتأثر بالأصغر من النافذتين، مع خصم البيانات اللي لسه في الطريق. زيادة سرعة المعالج مش هتحل تلقائيًا اختناق شبكة أو مستقبل مش بيقرأ.

الخوارزميات المختلفة ليها سياسات مختلفة. لا تفترض إن كل فقد معناه نفس رد الفعل أو إن كل نظام بيستخدم نفس خوارزمية الازدحام. المهم تفهم الفصل بين قدرة المستقبل وقدرة الطريق.

### احسب المتاح، مش حجم النافذة فقط

نفترض rwnd تساوي 6000 بايت، و cwnd تساوي 4000، وفيه 3000 بايت أُرسلت ولسه من غير تأكيد. الحد الأبسط هنا هو الأصغر 4000، فالمتاح لإرسال **بيانات جديدة** هو `4000 − 3000 = 1000` بايت، مش 4000 زيادة فوق الموجود.

لو rwnd أصبحت صفرًا، يتوقف إرسال البيانات الجديدة المعتاد؛ قد توجد رسائل فحص نافذة وفق البروتوكول. ولو cwnd هي الأصغر، تكبير مخزن المستقبل وحده لا يزيل حد الازدحام.

**جرّب:** rwnd=6000 و cwnd=5000، والموجود من غير تأكيد 3500. كم المتاح في النموذج؟

<details>
<summary>راجع الحساب</summary>

`min(6000, 5000) − 3500 = 1500` بايت. ده تبسيط ضمن مثال تدفق عادي؛ ليس معادلة توقيت أو وعد إرسال فورًا، لأن تفاصيل الاستعادة والجدولة لها أثر.

</details>

## تعمق الإغلاق: TIME_WAIT و Keepalive

**TIME_WAIT** حالة انتظار بعد الإغلاق المنظم عند الطرف المناسب، تساعد في التعامل مع المقاطع المتأخرة وإعادة تأكيد نهاية الاتصال. وجودها طبيعي. حذفها أو تقليلها عشوائيًا علشان «ننظف الاتصالات» ممكن يغيّر سلوك النظام بصورة غير محسوبة.

**Keepalive** في TCP ممكن يساعد يكتشف بعض الاتصالات الخاملة اللي مات طرفها حسب الإعدادات. مش هو نفسه إعادة استخدام اتصال HTTP، ومش بديل عن مهلة عمل واضحة لطلب التطبيق.

## تتأكد من إيه وقت العطل؟

لو ظهر `Connection refused`، افحص إن فيه برنامج بيستمع على العنوان والمنفذ المطلوبين. رفض الاتصال ممكن كمان يكون نتيجة سياسة شبكة بترد بالرفض. لو فيه Timeout، السبب ممكن يكون إسقاط مرور أو مشكلة توجيه أو طرف متأخر؛ الرسالة وحدها مش بتحسم السبب.

في PowerShell تقدر تراقب اتصالًا محليًا أثناء تشغيل المثال:

```powershell
Get-NetTCPConnection -LocalPort 9099 -ErrorAction SilentlyContinue
```

وعلى Linux:

```bash
ss -tn
```

الاتصال قصير، فممكن ينتهي قبل ما تلحق تشوفه. استخدم **Packet capture** لو محتاج تتبع المصافحة والتأكيد والإغلاق؛ ده تسجيل لحركة الشبكة وقد يكشف بيانات حساسة، فخليه في معملك المحلي. `ping` يستخدم ICMP، وبالتالي نجاحه مش إثبات إن خادم TCP على منفذ معين بيقبل اتصالات.

## راجع فهمك

<details><summary>كتبت رسالتين، لكن المستقبل قرأهما مع بعض. ده خطأ في TCP؟</summary>
لا. TCP بيقدم byte stream. محتاج تحدد حدود الرسالة بنهاية سطر أو طول أو صيغة بروتوكول واضحة.
</details>

<details><summary>جالك ACK وبعده فشل الدفع. فيه تناقض؟</summary>
لا. ACK يخص استلام طبقة النقل. الدفع له تحقق ومعاملة ورد تطبيق مستقل.
</details>

<details><summary>المصافحة نجحت لكن رفع ملف كبير اتوقف. تبدأ منين؟</summary>
افصل الفرضيات: هل التطبيق بيقرأ؟ هل فيه مهلة؟ هل فيه إعادة إرسال أو مشكلة Path MTU؟ اجمع دليلًا من التطبيق والاتصال بدل افتراض سبب واحد.
</details>

<details><summary>إيه الفرق بين FIN و RST؟</summary>
FIN ينهي الإرسال في اتجاه بطريقة منظمة، مع إمكانية استمرار الاتجاه الآخر. RST يعيد ضبط الاتصال بصورة مفاجئة.
</details>
