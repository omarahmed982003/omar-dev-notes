**Webhook — إشعار بين خادمين** طلب يرسله نظام عند حدث اتفقت عليه، مثل اكتمال عملية. العميل هنا برنامج خادم، مش تبويب المتصفح. هنبدأ بإشعار محلي واحد ثم نرسله مرتين لنفهم خطر تكرار الأثر.


## أرسل حدثًا مرتين

شغّل [المعمل](/programming-basics/32-local-network-lab/). في PowerShell اكتب:

```powershell
Set-Content -LiteralPath event.json -Value '{"id":"order-1"}' -Encoding ascii
curl.exe -i -H "Content-Type: application/json" --data-binary "@event.json" http://127.0.0.1:8766/webhook
```

الأمر الأول يكتب ملف نص فيه معرّف حدث للتدريب. `--data-binary` ترسل محتواه كما هو في طلب POST. المتوقع `duplicate:false` و`processedCount:1`. كرر أمر curl: يصبح `duplicate:true` والعدد يظل1؛ الخادم تذكر المعرّف فلم يكرر الأثر. غيّر المعرف إلى order-2 في الملف وأرسل: العدد2.

هذا مستقبل محلي يفقد ذاكرته بإعادة التشغيل، ولا يتحقق من توقيع مرسل خارجي. في خدمة حقيقية نحتاج تحقق المصدر وحفظ منع التكرار بشكل دائم؛ التفاصيل التالية تشرح ليه، من غير خلطها بأول رسالة نجربها.

## Webhooks

**Raw body — الجسم الخام** هو البايتات كما وصلت قبل تغيير المسافات أو تحويل JSON (JavaScript Object Notation؛ صيغة نصية لترتيب البيانات في أسماء وقيم وقوائم) إلى قيم. **HMAC، Hash-based Message Authentication Code** قيمة تحقق محسوبة من الرسالة ومفتاح سري مشترك. **Timestamp** وقت إنشاء الرسالة. **Replay** إعادة إرسال رسالة صحيحة قديمة لتنفيذ أثرها مرة أخرى. تختلف تفاصيل توقيع كل مزود، فاتبع عقده بدل افتراض صيغة واحدة.

المقطع البرمجي أسفل القائمة جزء توضيحي فقط: يفترض أن timestamp وrawBody وsecret وsignature قُرئت وفُحصت وفق عقد المزود. SHA-256 دالة تلخيص مستخدمة داخل HMAC، وhash_equals تقارن قيم التحقق بطريقة تتجنب تسريب الفارق من زمن المقارنة. المقطع وحده لا يفحص عمر الرسالة ولا يمنع تكرار الحدث:

المستقبل يجب أن:

1. يقرأ raw body.
2. يتحقق من توقيع HMAC وtimestamp قبل parsing الموثوق.
3. يرفض replay خارج نافذة زمنية.
4. يسجل event ID ويمنع المعالجة المكررة.
5. يعيد نجاحًا سريعًا ثم ينقل العمل الثقيل إلى queue (طابور يعالج العناصر عادة بترتيب وصولها).

```php
$expected = hash_hmac('sha256', $timestamp . '.' . $rawBody, $secret);
if (!hash_equals($expected, $signature)) {
    http_response_code(401);
    exit;
}
```

المُرسل يعيد المحاولة عند الفشل؛ لذلك idempotency ليست تحسينًا اختياريًا.

## الوصول مرة لا يعني المعالجة مرة

إعادة الاتصال لا تسترجع الرسائل تلقائيًا. **Sequence** رقم ترتيب، و**Cursor** علامة آخر موضع قرأه العميل، و**Snapshot** صورة للحالة الحالية؛ تختار منهم ما يسمح باستكمال العمل.

**Idempotent — أثر لا يتكرر عند إعادة نفس العملية** مهم للـwebhook. بعد فحص التوقيع والوقت، سجّل معرّف الحدث مع تغيير بيانات العمل في عملية قاعدة بيانات واحدة إما تنجح كلها أو تفشل كلها، أو استخدم آلية موثوقة تحقق نفس الضمان. لا تكتفِ بفحص «هل المعرّف موجود؟» ثم كتابة منفصلة؛ قد يصل طلبان معًا.

**تدريب محلول:** حدث دفع بمعرّف pay-42 وصل مرتين. اجعل المعرف فريدًا في سجل المعالجة؛ أول معالجة تسجل الدفع، والثانية تكتشف أنه عولج وتعيد ردًا مناسبًا بلا إضافة رصيد ثانية. لو شغلك يُرسل لطابور، أقرّ بالاستلام بعد حفظه بشكل موثوق، لا قبل حفظه ثم فقده عند توقف الخادم. الوصول المتأخر أو المختلف الترتيب يحتاج أيضًا مقارنة حالة الطلب وقواعد انتقالها.
