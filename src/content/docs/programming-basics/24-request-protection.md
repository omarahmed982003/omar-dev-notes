خادم قادر على تنفيذ طلب سليم قد يتعرض لطلبات ضارة أو أكثر من قدرته. هنفرق بين فحص الطلب وتنظيم عدد الطلبات.

## ثلاث طرق للعد بأرقام صغيرة

**Rate limit — حد معدل الطلبات** يقرر كم طلبًا نقبل خلال وقت. لو الحد 2 كل 10 ثوانٍ:

| الطريقة | الفكرة | أثرها |
|---|---|---|
| Fixed window — نافذة ثابتة | عداد يبدأ من جديد كل 10 ثوانٍ | قد يقبل طلبين آخر نافذة وطلبين أول التالية قريبين جدًا |
| Sliding window — نافذة متحركة | انظر للعشر ثواني السابقة للحظة الحالية | يتجنب نفس القفزة عند الحد، وله أكثر من طريقة تنفيذ |
| Token bucket — مخزن سماح | مخزن سعته 2، وكل 5 ثوانٍ نضيف سماحًا حتى السعة | طلبان فورًا لو ممتلئ، ثم انتظار التجديد؛ كل طلب يستهلك سماحًا |

بديل القراءة من غير Node.js: افترض عدادًا فاضيًا وحده 2 داخل نافذة 10 ثوانٍ واحدة؛ ثلاثة طلبات داخلها ينتج عنها 200،200،429. ده خرج توضيحي نفترض فيه عدم وجود طلبات أخرى. للتطبيق **اختياريًا**، [معمل Node.js](/programming-basics/32-local-network-lab/) يقدم `/limited` على 8766؛ جرّب في نافذة جديدة بعد تصفير عداده. `Retry-After` يقترح زمن انتظار. هذه نافذة ثابتة مشتركة للتجربة، مش سياسة عادلة لكل مستخدم. حماية محتوى الطلب موضوع مختلف عن عدد الطلبات.

## WAF ليس بديلًا لأمان التطبيق

**WAF، Web Application Firewall — جدار حماية تطبيق ويب** يفحص خصائص الطلب حسب قواعد. **Managed rules — قواعد جاهزة يديرها المزود** تكشف أنماطًا معروفة، ويمكن إضافة قواعد خاصة بتطبيقك. عند الاشتباه قد يحظر الطلب، أو ينفذ **Challenge — تحققًا إضافيًا من العميل**، أو يكتب **Log — سجل حدث** للمراجعة.

المشكلة إن طلب تعديل فاتورة قد يكون سليم الشكل لكن يخص مستخدمًا آخر. WAF لا يملك وحده كل قواعد العمل؛ التطبيق يظل مسؤولًا عن **Validation — فحص المدخلات**، والتحقق من الهوية والصلاحيات. و**Parameterized queries — استعلامات بمعاملات منفصلة عن نص الأمر** تمنع خلط البيانات بأوامر قاعدة البيانات؛ تفاصيلها في مسار قواعد البيانات، مش إعدادًا سحريًا داخل WAF.

**False positive — إنذار خاطئ** يعني أن القاعدة اشتبهت في طلب سليم. اختبر القواعد في وضع مراقبة قبل الحظر إن أمكن؛ القاعدة الواسعة قد توقف عملاء حقيقيين. وثّق الاستثناءات بمدة ومالك وسبب بدل تعطيل الحماية دائمًا.

## Rate Limiting وإدارة الاندفاع

يمكن حساب الحد حسب IP (Internet Protocol؛ قواعد عنونة الحزم وتوجيهها بين الشبكات، وعنوان IP رقم يحدد واجهة في هذا السياق) أو User ID أو API (Application Programming Interface؛ اتفاق يسمح لبرنامج بطلب بيانات أو عملية من مكوّن آخر) Key أو **Tenant — مؤسسة عميلة تشارك الخدمة** أو **Route — مسار معالجة الطلب**.

من النماذج Fixed Window وSliding Window وToken Bucket. يسمح Token Bucket باندفاع قصير حتى سعة الدلو ثم يحد المعدل المستمر.

أعد `429 Too Many Requests`، وأرسل `Retry-After` عندما تستطيع إعطاء قيمة صحيحة. لا تعتمد على IP وحده في كل الحالات؛ قد يشترك آلاف المستخدمين خلف NAT (Network Address Translation؛ تغيير عناوين IP أثناء مرور الحزم بين شبكات)، وقد يبدل المهاجم عناوينه.

فرّق بين Rate Limit لمنع الإساءة، وConcurrency Limit لمنع تشبع Workers (وحدة تنفيذ تتولى مهمة أو طلبًا؛ قد تكون عملية أو خيطًا حسب النظام)، و**Quota — حصة استهلاك** لخطة خلال يوم أو شهر. عند الضغط الشديد استخدم Backpressure (إبطاء المنتج عندما لا يستطيع المستهلك متابعة معدل البيانات) أو **Load shedding — رفض جزء من العمل وقت الضغط** بدل قبول عمل لن يكتمل.

راجع أثر القاعدة على الطلبات السليمة، وحدد **Rollback — طريقة رجوع لإعداد معروف** لو زادت الإنذارات الخاطئة بعد التغيير.
