معاك طلبات، وعايز إجمالي كل عميل. ممكن تجمع لكل عميل بتمرير جديد على الطلبات، أو تحفظ مجموعًا يتحدث في مرور واحد. **مقارنة الخوارزميات** معناها نقارن صحة الحل، وعدد خطواته، وذاكرته مع زيادة البيانات.

ابدأ بعد القوائم والحلقات والدوال في اللغة اللي بتذاكرها؛ للتطبيق بـ PHP ارجع إلى [مسار PHP](/php/). تقدر تتبع المثال يدويًا الأول. ده تعمق بعد أول برنامج، مش شرطًا قبل بدء لغة.

## اكتب العقد والنتيجة يدويًا

**المدخل** قائمة طلبات، في كل طلب `customer_id` رقم عميل صحيح موجب، و `total` إجمالي صحيح غير سالب بوحدة صغيرة زي القروش. **المخرج** مجموع الطلبات لكل عميل.

نرفض سجلًا مخالفًا بدل تجاهله بصمت. القائمة الفارغة ترجع جدولًا فارغًا. نرفض الجمع لو هيخرج عن مدى العدد الصحيح، بدل تحويل المبلغ لدقة تقريبية من غير قرار.

| الطلب | العميل | المبلغ | الإجماليات بعده |
|---|---: |---: |---|
| الأول | 1 | 100 | {1: 100} |
| الثاني | 2 | 50 | {1: 100, 2: 50} |
| الثالث | 1 | 20 | {1: 120, 2: 50} |

**Map — جدول مفاتيح وقيم** يربط معرف العميل بإجماليه. **Lookup — بحث بالمفتاح** يقرأ الإجمالي الحالي. العميل الجديد يبدأ بصفر؛ الصفر هنا بداية مجموع، مش تخمينًا لقيمة غير معروفة.

## خطوات الحل قبل الصياغة

**Pseudocode** وصف دقيق من غير لغة تنفيذ. `validate` هنا تعني افحص العقد، مش دالة جاهزة نفترض وجودها. `get` تقرأ القيمة أو تستعمل البداية صفرًا.

~~~text
totals = empty map
for each order in orders:
    validate order.customer_id and order.total
    old = totals.get(order.customer_id, default=0)
    totals[order.customer_id] = old + order.total
return totals
~~~

بعد كل طلب، الجدول يحتوي مجموع ما فحصناه لكل عميل. دي **Invariant — حقيقة محفوظة** تفسر صحة التجميع. **Precondition** المدخل مطابق للعقد، و**Postcondition** الناتج يحقق المجاميع المطلوبة. **Termination** مضمون لأننا نفحص عنصرًا جديدًا من قائمة محدودة كل دورة.

## نسخة PHP اختيارية كاملة

احفظ `totals.php` وشغله بـ `php totals.php` بـ PHP 8+. المثال يطبع فقط. نفترض معرفة arrays و foreach من PHP؛ الجدول هنا array بمفاتيح العملاء.

`is_array` تفحص إن العنصر سجل، و `isset` وجود الحقول غير null، و `is_int` نوع العدد الصحيح، و `||` تعني «أو». `throw` يرفض سجلًا غير صالح، و `?? 0` تستعمل صفرًا لو العميل جديد. `PHP_INT_MAX` حد العدد الصحيح في البيئة، و `OverflowException` إشارة فشل لتجاوز المدى؛ نفحص الحد قبل الجمع.

~~~php
<?php
declare(strict_types=1);

function totalsByCustomer(array $orders): array
{
    $totals = [];

    foreach ($orders as $order) {
        if (!is_array($order)
            || !isset($order['customer_id'], $order['total'])
            || !is_int($order['customer_id']) || $order['customer_id'] < 1
            || !is_int($order['total']) || $order['total'] < 0) {
            throw new InvalidArgumentException('Invalid order');
        }

        $id = $order['customer_id'];
        $old = $totals[$id] ?? 0;

        if ($order['total'] > PHP_INT_MAX - $old) {
            throw new OverflowException('Customer total exceeds integer range');
        }

        $totals[$id] = $old + $order['total'];
    }

    return $totals;
}

$orders = [
    ['customer_id' => 1, 'total' => 100],
    ['customer_id' => 2, 'total' => 50],
    ['customer_id' => 1, 'total' => 20],
];

foreach (totalsByCustomer($orders) as $id => $total) {
    echo $id . ':' . $total . PHP_EOL;
}
~~~

الخرج المتوقع:

~~~text
1:120
2:50
~~~

غيّر قائمة التدريب إلى `[]`: ما فيش سطور عملاء. الدالة ترفض العنصر غير المكتوب كسجل array، أو الحقل الناقص، أو النوع غير الصحيح. `PHP_INT_MAX` أكبر عدد صحيح تسعه بيئة PHP الحالية. `OverflowException` تعلن أن الجمع سيتجاوز هذا المدى؛ نفحص `القيمة الجديدة > الحد الأقصى − المجموع القديم` قبل الجمع، بدل اكتشاف التلف بعده. نجح هذا الفحص لأن القيم المقبولة غير سالبة.

## Big O: النمو مش عدد الثواني

**حجم المدخل n** هنا عدد الطلبات. **Time complexity — كلفة الوقت** تصف نمو العمل، و**Space complexity — كلفة المساحة** تصف الذاكرة المطلوبة. هنا نذكر الذاكرة الإضافية دون المدخل نفسه.

**Big O** يصف حدًا لنمو التكلفة، مش توقيتًا بالثواني. في الأمثلة المبسطة دي بنستعمله لوصف نمط النمو المعتاد المذكور مع افتراضاته.

| نمو الكلفة | الفكرة |
|---|---|
| O(1) | عدد خطوات لا يكبر مع n، زي وصول مباشر لموضع معلوم في مصفوفة تدعمه |
| O(log n) | استبعاد نصف نطاق مرتب كل مرة |
| O(n) | مرور مرة على n عنصر |
| O(n log n) | نمو شائع في خوارزميات فرز فعالة |
| O(n²) | مقارنة كل عنصر بكل عنصر |

**Logarithm — لوغاريتم** هنا يجاوب: كام مرة نقسم الحجم على 2 لحد 1؟ لـ 1024، عشر مرات. **Binary search — بحث ثنائي** يستبعد نصف النطاق المرتب: للبحث عن 7 في[1, 3, 5, 7, 9] نفحص 5، ثم نبحث في الجزء الأكبر. مش بيشتغل بنفس الضمان على بيانات غير مرتبة.

**الفرز** إعادة ترتيب العناصر حسب قاعدة. ثمن الفرز نفسه جزء من اختيار الحل، مش خطوة مجانية.

## ليه نوع الجدول يفرق؟

**Hash map — جدول تجزئة** يستخدم دالة لتحديد مكان البحث من المفتاح. مع توزيع مناسب وإدارة سعة، البحث والتحديث متوقعهما O(1)، فتجميع n طلب متوقعه O(n)، ومساحته O(k)، حيث k عدد العملاء المختلفين.

مش كل Map ضمان O(1): تصادم مفاتيح كثيرة قد يجعل البحث O(n) في تنفيذ تقليدي. جدول مرتب بشجرة قد يعطي O(log n) للعملية. اسم الواجهة وحده لا يحدد التنفيذ.

**Best / Average / Worst case** أفضل ومتوسط وأسوأ حالة. البحث الخطي عن أول عنصر قد ينتهي بعد مقارنة واحدة، وعن غائب يفحص الجميع. قول الحالة والافتراض قبل كتابة الكلفة.

## اختار البنية حسب السؤال

- **List/Array — قائمة أو مصفوفة:**  عناصر بمواقع، مع تفاصيل ترتيب ووصول حسب التنفيذ؛ مفيدة لو التكرار مهم.
- **Set — مجموعة:**  قيم مميزة بلا عداد تكرار؛ تنفع لسؤال «ظهرت قبل كده؟».
- **Queue — طابور:**  أول داخل أول خارج.
- **Stack — مكدس:**  آخر داخل أول خارج، زي رصة أطباق.

استخدام Set لاكتشاف التكرار قد يشتري وقتًا أقل بذاكرة إضافية. حل O(n) مش مضمونًا أسرع على قائمة صغيرة من كل حل أبسط؛ الثوابت والتخصيص مؤثران. ابدأ بالصحة والوضوح، وقِس تكرارات وأحجامًا مختلفة قبل التحسين.

## تعمق اختياري: نفس العقد في مسألة سلة

سعر غير سالب وكمية صحيحة لا تقل عن 1، وخصم من 0 إلى 100. نرفض المخالف قبل الحساب، ونختار تمثيل فلوس وسياسة تقريب صريحة عند التنفيذ.

~~~text
INPUT items, discountPercent
IF discountPercent < 0 OR discountPercent > 100:
    RETURN error
total = 0
FOR EACH item IN items:
    IF item.price < 0 OR item.quantity < 1:
        RETURN error
    total = total + item.price * item.quantity
RETURN total * (1 - discountPercent / 100)
~~~

الفكرة مش نوع syntax جديد: مدخلات، قواعد، خطوات، وناتج. نضيف فحص النوع والشكل وفق مصدر المدخل؛ pseudocode مش بديلًا للتحقق الخارجي.

## تعمق اختياري: الاستدعاء الذاتي

**Recursion — استدعاء ذاتي** دالة تستدعي نفسها لمسألة أصغر، مع حالة توقف. جمع القائمة ممكن يكون أول عنصر زائد مجموع الباقي، والتوقف عند الفراغ.

كل استدعاء ينتظر نتيجة التالي ويحتاج حالة محفوظة في مكدس الاستدعاءات؛ تنفيذ طويل قد يستهلك ذاكرة أكثر من حلقة. الاستدعاء الذاتي مش تحسينًا تلقائيًا.
