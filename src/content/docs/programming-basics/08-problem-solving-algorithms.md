ابدأ بعد التطبيق على المتغيرات والحلقات والقوائم في اللغة التي اخترتها.


## قبل التفاصيل

البرمجة تبدأ قبل الكود: حدّد المدخلات والمخرجات والقيود، واكتب خطوات يمكن اختبارها، ثم اختر بنية البيانات والتعقيد المناسبين للحجم.

## من المشكلة إلى برنامج

لا تبدأ بالكود. اكتب أولًا:

1. **المدخلات:** ما البيانات القادمة؟ وما حدودها؟
2. **المخرجات:** ما النتيجة المطلوبة بدقة؟
3. **القواعد:** ما الحالات العادية والاستثنائية؟
4. **التقسيم:** حوّل المشكلة إلى خطوات صغيرة قابلة للاختبار.
5. **التحقق:** جرّب مثالًا عاديًا، حدًا أدنى، حدًا أقصى، ومدخلًا غير صالح.

مثال: حساب إجمالي سلة بعد خصم.

```text
INPUT items, discountPercent
IF discountPercent < 0 OR discountPercent > 100
    RETURN error
total = 0
FOR EACH item IN items
    IF item.price < 0 OR item.quantity < 1
        RETURN error
    total = total + item.price * item.quantity
RETURN total * (1 - discountPercent / 100)
```

الـPseudocode يشرح المنطق بلا ارتباط بصياغة لغة، ثم يمكن تحويله إلى PHP (اسم لغة برمجة تستخدم كثيرًا لمعالجة طلبات الويب على الخادم) أو JavaScript أو غيرهما.

## اختيار بنية البيانات

| الحاجة | بنية مناسبة |
|---|---|
| ترتيب عناصر والسماح بالتكرار | List/Array |
| الوصول بقيمة مفتاح | Map/Associative Array |
| منع التكرار | Set |
| أول داخل أول خارج | Queue |
| آخر داخل أول خارج | Stack |

اختيار البنية يؤثر في وضوح الحل وكلفته. لا تستخدم nested loops تلقائيًا إذا كان Map يستطيع تحويل البحث المتكرر إلى lookup مباشر.

## التعقيد Big O

Big O يصف نمو الزمن أو الذاكرة مع نمو حجم الإدخال، وليس عدد الثواني الفعلي.

| التعقيد | مثال |
|---|---|
| `O(1)` | قراءة موضع معلوم في مصفوفة تدعم الوصول المباشر |
| `O(log n)` | Binary search في بيانات مرتبة |
| `O(n)` | المرور مرة على القائمة |
| `O(n log n)` | خوارزميات فرز فعالة شائعة |
| `O(n²)` | مقارنة كل عنصر بكل عنصر |

الأولوية للصحة والوضوح، ثم القياس قبل التحسين. خوارزمية `O(n)` قد تكون أبطأ على بيانات صغيرة من حل أبسط بسبب الثوابت.

## تمرين

لديك قائمة طلبات، وكل طلب يحوي `customer_id` و`total`. صمّم خوارزمية تعيد إجمالي كل عميل:

- اكتب المدخل والمخرج.
- عالج القائمة الفارغة والقيم السالبة.
- استخدم جدول تجميع؛ حلل الافتراض الذي يجعل زمنه المتوقع `O(n)` كما في الحل.
- اكتب ثلاث حالات اختبار قبل كتابة الكود.

## حل تمرين العملاء ومعنى اختيار البنية

**List/Array — قائمة أو مصفوفة** تحتفظ بعناصر يمكن الرجوع إليها بموضع، مثل [8,3,8]. **Map — جدول مفاتيح وقيم** يربط مفتاحًا بقيمة، مثل رقم العميل وإجماليه. **Set — مجموعة** تمنع تكرار القيمة. **Queue — طابور** يخرج الأقدم أولًا زي صف الانتظار، و**Stack — مكدس** يخرج الأحدث أولًا زي رصة أطباق. تفاصيل الترتيب والأداء تعتمد على تنفيذ البنية في اللغة.

**Lookup** يعني البحث عن قيمة. الوصول لموضع معلوم في مصفوفة عادة O(1). البحث بالمفتاح في **Hash map — جدول يستخدم دالة لتحويل المفتاح إلى مكان بحث** متوسطه المتوقع O(1) بافتراض توزيع مناسب وإدارة سعة؛ الأسوأ قد يكون O(n) في تنفيذ تقليدي عند تزاحم مفاتيح كثيرة. جدول مرتب بشجرة قد يوفر O(log n) بدلًا منه. لذلك جملة «كل Map ثابت الوقت» غلط.

**Binary search — بحث ثنائي** يستبعد نصف النطاق المرتب كل مرة: للبحث عن7 في [1,3,5,7,9] نفحص5، ثم نكمل في الجزء الأكبر. log₂n يسأل كم مرة نقسم n على2 حتى يبقى1؛ مثلًا1024 تحتاج10 مرات. الفرز يعني إعادة ترتيب العناصر حسب قاعدة، مثل من الأصغر للأكبر.

عقد تمرين العملاء: كل طلب له رقم عميل صحيح موجب وإجمالي غير سالب، ونرفض غير ذلك. هنفترض الأرقام هنا بوحدات عملة صحيحة صغيرة، مثل القروش، لتجنب تقريب الكسور. القائمة الفارغة ترجع جدولًا فارغًا.

```text
totals = empty map
for each order in orders:
    validate order.customer_id and order.total
    old = totals.get(order.customer_id, default=0)
    totals[order.customer_id] = old + order.total
return totals
```

get تقرأ القيمة وتستعمل0 لو العميل جديد، وvalidate تطبق قواعد الصلاحية المذكورة وليست دالة جاهزة في لغة. للطلبات (عميل1،100)، (عميل2،50)، (عميل1،20)، الناتج {1:120,2:50}. إجمالي−1 مرفوض. مع Hash map مناسبة، الزمن المتوقع O(n) والذاكرة O(k) لعدد k من العملاء المختلفين، غير مساحة المدخل نفسه.

**Precondition** شرط صالح قبل التنفيذ، و**Postcondition** ما يجب أن يحققه الناتج. **Invariant** هنا: بعد كل طلب، الجدول يحتوي مجموع الطلبات التي فحصناها لكل عميل. **Termination** انتهاء الحلقة مضمون لأن القائمة محدودة. **Recursion — استدعاء ذاتي** تحتاج حالة توقف؛ مثل جمع القائمة بإضافة أول عنصر لمجموع الباقي، والتوقف عند القائمة الفارغة. كل استدعاء ينتظر نتيجة التالي ويستهلك مساحة في مكدس الاستدعاءات، لذلك التكرار الطويل قد يكون أبسط وأقل استهلاكًا.

**تدريب محلول:** أكبر قيمة في [−4] هي−4، وفي قائمة فارغة نرجع «لا توجد قيمة» وفق العقد. بعد فحص كل عنصر، المتغير largest يجب أن يمثل أكبر ما فحصناه؛ تهيئته بصفر تفشل مع القوائم السالبة.


## Best وAverage وWorst Case

قد يختلف عدد العمليات باختلاف المدخل. يجد البحث الخطي الهدف في أول عنصر في أفضل حالة، وقد يفحص العناصر كلها في أسوأ حالة. عند مقارنة الخوارزميات اذكر الحالة المقصودة ولا تكتب Big O بلا تفسير.

## Time وSpace Complexity

يقيس Time Complexity نمو عدد العمليات، ويقيس Space Complexity الذاكرة الإضافية. قد نستبدل الزمن بذاكرة إضافية، مثل استخدام Set لتسريع اكتشاف التكرار. تجاهل الثوابت لا يعني أنها غير مهمة عمليًا، لكنه يوضح السلوك عند نمو `n`.

## تصميم الاختبارات

قسّم المدخلات إلى فئات متكافئة، ثم اختبر الحدود والفارغ والقيمة الواحدة والتكرار والقيم الكبيرة والمدخل غير الصالح. اختبر Overflow والعمليات التي تغير الفرع. اكتب النتيجة المتوقعة يدويًا قبل تشغيل البرنامج حتى لا تفسر خرجه على أنه صحيح لمجرد أنه يبدو معقولًا.
