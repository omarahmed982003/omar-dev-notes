ابدأ بعد تجربة تغيير صفحة وقياس حجمها. **Module — وحدة كود** ملف يعلن ما يتيحه وما يحتاجه من ملفات أخرى. **Dependency graph — رسم الاعتماد** يربط الملف بما يحتاجه؛ لو A يستورد B، لازم تتجهز B وفق قواعد التحميل قبل تنفيذ ما يعتمد عليها. هنربط التفاصيل باستجابة الصفحة.


## JavaScript والتحميل

```html
<script src="/app.js" defer></script>
<script type="module" src="/main.js"></script>
```

`defer` يسمح باستمرار parsing وينفذ بعد اكتمال DOM وبالترتيب. الـmodules مؤجلة افتراضيًا ولها dependency graph. أما `async` فينفذ عند اكتمال التحميل دون ضمان ترتيب.

تغيير layout بصورة متكررة داخل loop قد يسبب layout thrashing. اجمع القراءات ثم الكتابات، وحرّك العناصر غالبًا عبر `transform` عندما يناسب.

## دورة حدث مبسطة

JavaScript يعمل عادة على main thread (خيط تنفيذ: مسار تعليمات داخل عملية) مع event loop. المهام الطويلة تؤخر input والرسم. قس Largest Contentful Paint وInteraction to Next Paint وCumulative Layout Shift.

## ليه التحميل الثاني ممكن يختلف؟

**Redirect — إعادة توجيه** رد يطلب من المتصفح زيارة عنوان آخر؛ فتبدأ رسالة طلب جديدة، لكن مش لازم اتصال جديد. **Connection reuse — إعادة استخدام الاتصال** معناها إرسال طلب آخر على اتصال موجود بدل تكرار البداية. **Service Worker (ملف JavaScript يسجله الموقع لدى المتصفح؛ يستجيب لأحداث مثل طلب ملف، ويمكنه تقديم نسخة محفوظة وفق قواعد الموقع)** برنامج يسجله الموقع في المتصفح، ويمكنه التعامل مع بعض الطلبات واستخدام نسخ محلية حسب كوده.

في أدوات المطور **DevTools**، افتح لوحة **Network — الشبكة** قبل إعادة التحميل. رسم **Waterfall — التوقيت المتتابع** يعرض شريطًا لكل طلب يوضح متى بدأ وكم استغرق. شوف أول تحميل والثاني، وافتح تفاصيل طلب الصفحة. **Cookie** قيمة صغيرة يحفظها المتصفح ويرسلها مع الطلبات المناسبة؛ و**CORS** قواعد سماح لقراءة رد موقع آخر داخل JavaScript، هنفصلها في درسها.

**تدريب وحل:** اختفت مرحلة الاتصال في الطلب الثاني؛ هل ده يثبت أن الصفحة جاءت من التخزين المؤقت؟ لا. ممكن الاتصال اتعاد استخدامه والرد جاء من الخادم. ابحث عن عبارة تشير لنسخة محلية أو رؤوس الرد، وهي معلومات تصف الرسالة، ولا تستنتج من السرعة وحدها.
