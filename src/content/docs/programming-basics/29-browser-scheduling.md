ملفان اتحمّلوا، لكن الكود اللي يحتاج الإعدادات اشتغل قبلها. وزرار اتضغط، لكن استجابته اتأخرت رغم وصول البيانات. التحميل والتنفيذ والرسم مش خطوة واحدة؛ هنفصلهم بتتبع صغير.

ده تعمق بعد أساس HTML و JavaScript، مش شرطًا قبل أول صفحة. **HTML** وصف عناصر المستند، و**DOM — نموذج عناصر الصفحة في الذاكرة** يسمح للكود بقراءتها وتعديلها. لو لسه ما كتبتش دالة، ابدأ بالجداول وارجع للكود بعد أساس اللغة.

## JavaScript والتحميل

**Parsing — تحليل HTML** بناء نموذج المستند من النص. **Script** برنامج JavaScript، و**Module — وحدة كود** ملف يعلن ما يتيحه وما يستورده. **Dependency graph — رسم الاعتمادات** يربط الوحدة بالوحدات التي تحتاجها.

**تحميل الملف** وصول بايتاته؛ **تنفيذه** تشغيل تعليماته. تنزيل app قبل config لا يثبت أنه المفروض يتنفذ قبله.

| الشكل لملف خارجي داخل HTML | التحميل | التنفيذ في المثال العادي |
|---|---|---|
| script عادي من غير async أو defer | قد يوقف التحليل عنده | ينفذ ثم يكمل التحليل |
| script مع defer | يتداخل مع استمرار التحليل | بعد التحليل، ويحفظ ترتيب ملفات defer التقليدية |
| script مع async | يتداخل مع التحليل | عند جاهزيته؛ لا يضمن ترتيب الملفات المستقلة |
| type="module" من غير async | يجلب الوحدة واعتماداتها | مؤجل افتراضيًا، والتنفيذ يحترم علاقات الاعتماد |

دي أمثلة وسوم توضّح السياسة، مش تطبيقًا كاملًا بملفات جاهزة:

~~~html
<script src="/app.js" defer></script>
<script type="module" src="/main.js"></script>
~~~

لو app تقرأ إعدادًا تنشئه config، استعمال async للملفين لا يثبت أن config سبقت. لملفين تقليديين مع defer، ضعهما بترتيب الاعتماد؛ أو صرّح بالاعتماد عبر import في نظام الوحدات. **Import — استيراد** طلب كود معلن من وحدة أخرى؛ تفاصيل الصياغة في JavaScript.

## دورة حدث مبسطة

**Main thread — خيط الواجهة الرئيسي** ينفذ JavaScript المرتبط هنا بالصفحة، ويشارك في عمل الواجهة. **Task — مهمة** دور تنفيذ، مثل تشغيل السكربت أو معالجة نقرة أو callback مؤقت. **Callback — دالة نمررها لجهة أخرى لتستدعيها**؛ في تجربة المؤقت والوعد هنا تستدعيها المنصة لاحقًا، لكن مش كل callback في البرمجة غير متزامنة.

في المثال هنا، تعليمات السكربت المتزامنة تكمل من غير ما callback مؤقت أو وعد جاهز تقاطعها على نفس الخيط. **Microtask — مهمة دقيقة** مثل handler في then لوعد جاهز؛ تُعالج عند نقطة مناسبة بعد انتهاء العمل الحالي، قبل بدء مهمة عادية تالية. **Event loop — دورة الحدث** تنظم فرص تشغيل هذه الأعمال وتحديث العرض.

مش كل مهمة ينتج بعدها رسم فورًا؛ browser يختار فرص تحديث العرض. وإضافة مهام دقيقة بلا توقف قد تؤخر باقي العمل أيضًا.

## ملف كامل تتوقع خرجه

احفظ `event-loop.html` في مجلد تدريب جديد وافتحه في متصفح حديث. لا يحتاج Node أو خادمًا، ولا يتصل بالإنترنت. بنستخدم JavaScript هنا لأن ده موضوع آلية browser نفسها، مش تغيير لغة الأمثلة العامة.

قبل الكود:

- `const` تسمي قيمة، و`document.querySelector` تختار عنصرًا من DOM.
- `textContent` محتوى العنصر النصي، و`+=` تضيف نصًا لما قبله.
- `log` دالة نكتبها لعرض سطر. `() =>` صياغة دالة قصيرة نمررها كـ callback.
- `setTimeout` تجهز callback كمهمة بعد حد انتظار؛ الصفر ليس موعد تنفيذ فوريًا.
- `Promise.resolve()` تصنع وعدًا جاهز النتيجة، و`then` تسجل callback دقيقة؛ جاهزية الوعد لا تنفذ callback داخل هذا السطر فورًا.

~~~html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Event loop trace</title>
</head>
<body>
  <pre id="output"></pre>
  <script>
    const output = document.querySelector('#output');

    function log(message) {
      output.textContent += message + '\n';
    }

    log('A');
    setTimeout(() => log('D'), 0);
    Promise.resolve().then(() => log('C'));
    log('B');
  </script>
</body>
</html>
~~~

الخرج المتوقع، بالترتيب:

~~~text
A
B
C
D
~~~

| اللحظة | الشغل الحالي | العمل المنتظر | المعروض حتى الآن |
|---|---|---|---|
| log A | سكربت البداية | لا شيء من المثال | A |
| setTimeout | نفس السكربت مستمر | timer callback | A |
| then | نفس السكربت مستمر | microtask C و timer D | A |
| log B | السكربت يكمل | C ثم فرصة D لاحقًا | A،B |
| انتهاء السكربت | معالجة C الدقيقة | D | A،B،C |
| فرصة مهمة المؤقت | تنفيذ D | انتهى المثال | A،B،C،D |

كتابة المؤقت قبل then ما جعلتش D تسبق C. ولا الوعد الجاهز جعل C تقاطع السطر التالي داخل السكربت. ترتيب المثال ده محدد؛ **الزمن بالمللي ثانية مش محدد**.

## ليه الضغط والرسم ممكن يتأخروا؟

تخيل callback بدأت عند 0 وظلت تحسب حتى 80 مللي ثانية. حدث نقرة أو مؤقت أصبح جاهزًا عند 10 لا يجعل callback جارية تتوقف تلقائيًا؛ ينتظر دورًا مناسبًا. تعديل نص عنصر أثناءها لا يضمن أن المستخدم شافه في نفس اللحظة؛ تحديث DOM غير ظهور بكسلات جديدة.

دي أزمنة افتراضية لتفسير الانتظار، مش قياس جهازك. ما نشغّلش حلقة طويلة بلا حد للتجربة. الحل يُختار بعد القياس: تقسيم عمل، تأجيل جزء، أو Worker مناسب عند الحاجة، مش افتراض أن async تقسم أي حساب تلقائيًا. **Web Worker** بيئة تنفيذ خلفية لبعض الأعمال، لا تعدل DOM مباشرة.

**Layout — حساب مواضع وأحجام العناصر**. لو تغيّر المظهر ثم تطلب قياسًا ثم تغيّر وتقرأ ثانية في حلقة، قد تُجبر browser على حسابات متكررة؛ ده **Layout thrashing**. اجمع القراءات والكتابات عندما يناسب. تحريك عبر transform قد يقلل كلفة layout في حالات، لكنه مش ضمان تسريع لكل عنصر.

## تقيس إيه بدل حفظ أسماء؟

- **LCP، Largest Contentful Paint:** توقيت ظهور أكبر عنصر محتوى مؤهل في مساحة العرض، لفهم جانب من التحميل المرئي.
- **INP، Interaction to Next Paint:** مقياس استجابة التفاعلات حتى تحديث عرض لاحق؛ الانتظار والتنفيذ والعرض مؤثرون، مش زمن callback وحده.
- **CLS، Cumulative Layout Shift:** مقياس تحرك التخطيط غير المتوقع؛ ممكن شبكة سريعة ويظل المحتوى ينط أمام المستخدم.

افتح Performance في **DevTools — أدوات المطور** وشوف العمل الطويل وتوقيته. الأسماء دي تختار السؤال الذي تقيسه، مش خطوات نضبطها كلها بنفس الحل.

## ليه التحميل الثاني ممكن يختلف؟

**Redirect — إعادة توجيه** يبدأ طلبًا لعنوان آخر، مش بالضرورة اتصالًا جديدًا. **Connection reuse — إعادة استخدام اتصال** يرسل طلبًا آخر على اتصال موجود. **Service Worker** برنامج يسجله الموقع في browser، وقد يعترض بعض طلباته ويقدم محتوى محفوظًا وفق كوده؛ مش نفس سكربت DOM اللي فوق.

في Network، رسم **Waterfall — أشرطة توقيت الطلبات** يوضح البداية والمراحل. قارن أول تحميل والثاني. اختفاء مرحلة الاتصال لا يثبت HIT؛ قد أُعيد استخدام الاتصال ووصل الطلب للخادم. ابحث عن دليل مصدر الرد وسياسة الكاش.

**Cookie** قيمة يحتفظ بها browser ويرسلها مع الطلبات المناسبة؛ **CORS** سياسة سماح لقراءة بعض الردود عبر الأصل داخل JavaScript. لها [درس مستقل](/programming-basics/11-same-origin-cors/)، فلا نستنتجها من سرعة التحميل.

## تمرين مستقل

1. أضف `log('X');` بعد log B. توقع كل السطور قبل إعادة فتح ملف التدريب.
2. بدل سطر Promise كله بـ`log('C');` مباشرة. ما الترتيب الآن، وليه؟
3. هل setTimeout بقيمة 0 يضمن التنفيذ قبل السطر التالي؟ وهل يضمن قبل الرسم دائمًا؟
4. config و app ملفان تقليديان مستقلان مع async. app تحتاج config. هل ترتيب الوسمين يكفي؟
5. الطلب الثاني بلا مرحلة اتصال؛ هل ده دليل كافٍ أن Service Worker خدمه؟
