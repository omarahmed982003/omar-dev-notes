المتصفح بعت طلبين لنفس الموقع. إزاي الخادم يعرف إنهم لنفس الزائر، مع إن HTTP نفسه مش بيحتفظ بذاكرة مستخدم؟ هنمشي وراء طلبين، وبعدها نجرب جلسة PHP محلية. محتاج تعرف **Request — طلب** و**Response — رد** من [درس رسائل HTTP](/programming-basics/05-http-messages-state/).

## الأساس: المتصفح يحتفظ بمعرّف، والخادم يحتفظ بالحالة

**Cookie — ملف تعريف ارتباط** قيمة صغيرة يحفظها المتصفح ويرسلها تلقائيًا مع الطلبات التي تنطبق عليها قواعدها. مش لازم تكون ملفًا مستقلًا ظاهرًا في مجلد، ومش كل Cookie معناها تسجيل دخول.

**Session — جلسة تطبيق** حالة تربط عدة طلبات ببعض. في النموذج هنا، بيانات الجلسة موجودة عند الخادم، والمتصفح معاه معرّف عشوائي فقط. المعرّف لا يحتوي عدد الزيارات ولا كلمة السر.

**Stateless — عديم الحالة** معناه إن HTTP لا يستنتج وحده رابطًا بين طلبين. التطبيق هو اللي يبني الرابط بمعلومة يرسلها العميل؛ ده مش معناه إن الخادم ممنوع يحفظ بيانات.

## امشِ وراء الطلبين

القيمة `demo-id` في العرض التالي رمز توضيحي، مش معرّفًا صالحًا تختاره في تطبيق حقيقي:

~~~http
GET /counter.php HTTP/1.1
Host: 127.0.0.1:8088

HTTP/1.1 200 OK
Set-Cookie: FOUNDATIONSLAB=demo-id; Path=/; HttpOnly; SameSite=Lax
Cache-Control: no-store

{"visits":1}
~~~

**Set-Cookie — احفظ القيمة دي** حقل في **الرد**. المتصفح يحفظ المعرّف وفق قواعده. الخادم يربط نفس المعرّف ببيانات زي `visits = 1`.

~~~http
GET /counter.php HTTP/1.1
Host: 127.0.0.1:8088
Cookie: FOUNDATIONSLAB=demo-id

HTTP/1.1 200 OK
Content-Type: application/json

{"visits":2}
~~~

**Cookie — القيم المحفوظة المناسبة** حقل في **الطلب**. الخادم يستخدم المعرّف للوصول للحالة ثم يزيد العداد. مش لازم يعيد Set-Cookie في كل رد إذا لم يحتج تعديلها.

لو المتصفح ما بعتش المعرّف، قد يبدأ الخادم جلسة جديدة. ولو فتح مستخدم آخر الموقع، له معرّف مختلف. **معرّف الجلسة سر اعتماد** في جلسة الدخول؛ اللي يسرقه قد ينتحل صاحبها، فلا تنشره في صورة أو سجل عام.

## خصائص Cookie: كل واحدة بتحمي إيه؟

**Attribute — خاصية** إعداد بعد قيمة Set-Cookie. الخصائص مش جزءًا من القيمة، والمتصفح لا يعيد نسخها كلها في حقل Cookie.

| الخاصية | وظيفتها وحدودها |
|---|---|
| `Secure` | تقصر إرسال Cookie على اتصال آمن وفق قواعد المتصفح؛ لا تشفّر ملف التخزين ولا تعالج اختراق الخادم |
| `HttpOnly` | تمنع JavaScript الصفحة من قراءتها بواجهات Cookie المعتادة؛ المتصفح يقدر يرسلها مع الطلب، فلا تمنع كل أثر لـXSS |
| `SameSite=Lax` أو `Strict` | تقيد الإرسال في سياقات بين مواقع مختلفة؛ Lax تسمح ببعض التنقلات العليا الآمنة، وStrict أشد تقييدًا |
| `SameSite=None; Secure` | تسمح بسياقات cross-site عندما تسمح بقية سياسات المتصفح؛ ليست تصريحًا بتجاهل قيود Cookies الخارجية |
| `Path=/` | تجعل المسار مؤهلًا لإرسالها عبر مسارات الموقع؛ Path مش حاجز صلاحيات بين تطبيقات غير موثوقة |
| `Domain` | توسّع النطاق المؤهل عند ضبطها؛ حذفها يجعل Cookie خاصة بالمضيف الذي ضبطها |
| `Max-Age` أو `Expires` | يحددان بقاء Cookie؛ من غيرهما هي Session cookie، وقد تستعيدها خاصية استرجاع الجلسة في المتصفح |

**Site — موقع** في SameSite ليس هو **Origin — أصل** المكوّن من scheme وhost وport؛ قد يختلف الأصلان ويبقيان نفس الموقع. وCookies مش معزولة برقم المنفذ مثل قواعد Origin.

هندرس **CSRF — تزوير طلب عبر موقع آخر** في مسار الأمان. SameSite تقلل بعض الحالات، لكنها مش بديلًا عامًا عن تحقق الصلاحيات وحماية العمليات المعدِّلة.

## تجربة PHP اختيارية: عدّاد محلي بين طلبين

التجربة تحتاج [تجهيز PHP](/php/00-lab-setup/)، ولا تحتاج Node.js. استخدم PHP 8.3 أو أحدث كما في تجهيز المسار، ومجلد تدريب جديد وفاضي. مفيش حساب دخول حقيقي ولا بيانات شخصية.

داخل مجلد التدريب أنشئ مجلدين: `public` للكود المتاح عبر HTTP، و`session-data` لحالة الجلسات **خارج** المجلد المتاح. من PowerShell داخل مجلد التدريب:

~~~powershell
New-Item -ItemType Directory -Path public, session-data
~~~

`New-Item` ينشئ المجلدين؛ لو موجودين استخدم مجلد تدريب جديد بدل الكتابة فوق ملفاتك. احفظ الملف التالي باسم `public/counter.php`:

~~~php
<?php
declare(strict_types=1);

session_name('FOUNDATIONSLAB');
session_set_cookie_params([
    'lifetime' => 0,
    'path' => '/',
    'secure' => false,
    'httponly' => true,
    'samesite' => 'Lax',
]);
if (!session_start(['use_strict_mode' => 1])) {
    throw new RuntimeException('Session could not start');
}

$_SESSION['visits'] = ($_SESSION['visits'] ?? 0) + 1;
$visits = $_SESSION['visits'];
session_write_close();

header('Content-Type: application/json; charset=utf-8');
header('Cache-Control: no-store');
echo json_encode(['visits' => $visits], JSON_THROW_ON_ERROR);
~~~

`session_name` يختار اسم Cookie. `session_set_cookie_params` يضبط خصائصها **قبل** بدء الجلسة. `session_start` يستعيد الجلسة الموجودة أو ينشئ واحدة، وstrict mode يرفض استعمال معرّفات غير مهيأة في مخزن الجلسات المعتاد.

`$_SESSION` مجموعة القيم المرتبطة بالجلسة. `?? 0` يستخدم صفرًا عند غياب العداد. `session_write_close` يحفظ الحالة ويفك قفلها، و`json_encode` يحول النتيجة لنص JSON. نرسل الرؤوس قبل أي إخراج.

شغّل من مجلد التدريب، مش من `public`:

~~~powershell
php -d session.save_path=./session-data -S 127.0.0.1:8088 -t public
~~~

`-d` يضبط مكان الجلسات لهذه العملية فقط، و`-S` يبدأ خادم التطوير، و`-t public` يقصر ملفات الويب على public. الخادم يستمع على الجهاز نفسه فقط؛ مش خادم إنتاج. اترك الطرفية مفتوحة.

في طرفية ثانية **داخل نفس مجلد التدريب**:

~~~powershell
curl.exe -i -c cookies.txt http://127.0.0.1:8088/counter.php
curl.exe -i -b cookies.txt -c cookies.txt http://127.0.0.1:8088/counter.php
curl.exe -i http://127.0.0.1:8088/counter.php
~~~

`-c` يحفظ Cookies في ملف التدريب ويحدّثه، و`-b` يقرأها للطلب التالي. الملف يُكتب في كل أمر فيه -c؛ استخدم الاسم ده داخل المجلد الجديد فقط. على Linux وmacOS استخدم `curl` بدل `curl.exe`.

المتوقع في تجربة جديدة: `visits:1` ثم `visits:2` ثم `visits:1`؛ الثالث ما قرأش الملف، فبدأ جلسة مختلفة. معرّفات الجلسات عشوائية، فلا تتوقع قيمة ثابتة.

في المتصفح أعد تحميل نفس العنوان مرتين، وافحص Set-Cookie وCookie في Network؛ لا تخلط `localhost` بـ`127.0.0.1`. المتصفح وcurl لهما مخزنا Cookies منفصلان.

**حد الأمان:** `secure => false` مقصودة لهذا المعمل HTTP المحلي فقط. جلسة دخول منشورة تحتاج HTTPS وSecure وإعدادات وتجديد معرّف عند تغير صلاحية الدخول. المعمل يعد مشاهدات للشرح؛ مش تصميم تسجيل دخول ولا عدّاد تحليلات يعتمد عليه.

ملفات session-data وcookies.txt تحتوي حالة أو معرّفات تدريب؛ لا ترفعها للمستودع. أوقف الخادم بـCtrl+C بعد الانتهاء.

## خليك هنا في المرور الأول

المطلوب قبل الانتقال: تشرح مين أرسل Set-Cookie، ومين أرسل Cookie، وفين محفوظ عدد الزيارات، وليه الأمر الثالث بدأ من 1. القسم التالي تعمق HTTP مستقل عن حفظ جلسة المستخدم، ويمكن الرجوع له بعد تطبيق محلي.

## تعمق: التمثيل المناسب ومنع ضياع تعديل

**Content negotiation — اختيار تمثيل** معناه تقديم نسخة تناسب العميل: Accept لنوع البيانات، وAccept-Language للغة، وAccept-Encoding للضغط. **Vary** يحدد حقول الطلب التي تفرق بين النسخ في مخزن HTTP المؤقت.

**ETag — Entity Tag** معرّف لنسخة تمثيل المورد. **If-None-Match** يطلب المحتوى عند اختلاف النسخة ويفيد في فحص نسخة محفوظة؛ تفاصيله في [درس الكاش](/programming-basics/10-http-caching-compression/).

**If-Match — نفّذ لو النسخة ما زالت مطابقة** شرط يمنع **Lost update — ضياع تعديل** بسبب كتابة عميل فوق تعديل أحدث:

1. عمر يقرأ المنتج مع ETag يساوي `"v7"`.
2. منى تعدّل المنتج؛ نسخته الآن `"v8"`.
3. عمر يرسل تعديلًا ومعه `If-Match: "v7"`.
4. الخادم يرفض بـ`412 Precondition Failed`، أي فشل شرط مسبق، بدل مسح تعديل منى.

الفحص والكتابة لازم يكونا **Atomic — وحدة لا يتخللها تعديل منافس** بالنسبة للعملية؛ مقارنة الشرط ثم كتابة منفصلة ممكن تترك سباقًا. العميل يعيد قراءة الأحدث ويقرر طريقة حل التعارض.

## Token مش اسمًا آخر لـSession

**Token — رمز اعتماد** قيمة يقدمها العميل لإثبات إذن وفق تحقق الخدمة. بعض الرموز عشوائية وبعضها له صيغة منظمة؛ **JWT، JSON Web Token** صيغة تحمل ادعاءات، مش كل Token من نوع JWT.

الرمز ممكن ينتقل في Authorization، وقد يُستخدم Cookie لحمله حسب التصميم. طريقة النقل وحدها لا تحسم مكان حفظ الحالة ولا تلغي منع الإعادة أو الصلاحيات. المقارنة التفصيلية والتسجيل والخروج لها مسار الأمان؛ لا تختار JWT لمجرد أن HTTP عديم الحالة.

## راجع فهمك

<details><summary>حذفت Cookie من المتصفح. هل حذفت بيانات الجلسة من الخادم فورًا؟</summary>
لا. حذفت قدرة المتصفح الحالية على تقديم المعرّف؛ انتهاء أو إبطال البيانات عند الخادم له سياسة مستقلة. ده مختلف عن تنفيذ خروج آمن.
</details>

<details><summary>هل HttpOnly تمنع إرسال Cookie مع طلب نفّذه JavaScript؟</summary>
لا. تمنع قراءتها بواجهات JavaScript المعتادة، لكن المتصفح قد يرفقها بطلب مناسب. لذلك لا تلغي خطر XSS أو الحاجة للصلاحيات.
</details>

<details><summary>هل If-Match يثبت هوية صاحب التعديل؟</summary>
لا. هو شرط نسخة. الخادم لازم يفحص الهوية والصلاحيات أيضًا قبل تنفيذ تعديل مسموح.
</details>

الخلاصة: HTTP لا يبني جلسة مستخدم تلقائيًا؛ التطبيق يربط الطلبات بمعرّف. وشرط نسخة المورد يحل مشكلة مختلفة هي التعديل المتزامن.
