## خادم واحد يوضح الفكرة

جهّز [المعمل المحلي](/programming-basics/32-local-network-lab/). افتح `/api/products/1` على منفذ8766: الخادم يقرأ المسار، يختار بيانات المنتج، ويكوّن JSON، ثم يرسل الحالة200 والجسم. غيّر1 إلى2 فتجد404. **Route — مسار معالجة** قاعدة تربط عنوانًا بعمل ينفذه البرنامج.

```text
Browser → one server → choose route → build response → Browser
```

افحص سطر الطلب في الطرفية واربطه بالحالة في Network. دلوقتي عندنا سبب لفهم كل مرحلة. الوسيط في الدرس التالي يضيف جهة أخرى أمام هذا الخادم؛ مش شرطًا لعمل أول طلب.

## قبل التفاصيل

هذا الدرس يتتبع الطلب بعد وصوله إلى البنية الخلفية. الهدف ليس حفظ أسماء الأدوات، بل معرفة حدود المسؤولية حتى تبحث عن العطل في الطبقة الصحيحة.

## ما السيرفر؟

كلمة **Server** تصف دورًا، لا شكل جهاز بعينه. قد تعني:

- **جهازًا فعليًا أو Virtual Machine (جهاز افتراضي: بيئة تحاكي جهازًا وتشغل نظامًا وتطبيقات)** يوفّر CPU (Central Processing Unit؛ المعالج الرئيسي الذي ينفذ التعليمات) وRAM (Random Access Memory؛ ذاكرة العمل التي تحمل بيانات وتعليمات البرامج النشطة) وشبكة وتخزينًا.
- **برنامجًا** يستمع على عنوان IP (Internet Protocol؛ قواعد عنونة الحزم وتوجيهها بين الشبكات، وعنوان IP رقم يحدد واجهة في هذا السياق) ومنفذ ويجيب وفق Protocol، مثل Nginx أو PostgreSQL.
- **دورًا في تفاعل محدد:** البرنامج الذي يطلب خدمة هو Client، والذي يقدمها Server. وقد يكون التطبيق نفسه Client لخادم قاعدة البيانات.

يبدأ Server Process (عملية: نسخة برنامج تعمل بذاكرة وحالة وموارد) عادة بفتح Socket (واجهة اتصال ينشئها البرنامج؛ نقطة شبكة منها ترتبط عادة ببروتوكول وعنوان ومنفذ) وربطه بعنوان ومنفذ ثم الاستماع. عندما يصل اتصال، يقرأ الطلب ويتحقق منه وينفذ العمل ويرسل استجابة. تشغيل `localhost:8000` لا يعني وجود جهاز مستقل؛ يعني أن Process على جهازك يستمع محليًا على المنفذ `8000`.

يمكن لجهاز واحد تشغيل Web Server (خادم ويب يستقبل طلبات الويب ويعيد ملفات أو يمرر العمل للتطبيق) وApplication Server (برنامج يشغّل منطق التطبيق ويبني نتيجته) وDatabase (قاعدة بيانات: تخزين منظم يمكن البحث فيه وتعديله بقواعد) في التطوير، بينما تفصلها بيئة الإنتاج لأسباب التوسع والعزل والأمان. وعبارة «السيرفر وقع» غير دقيقة حتى نحدد: هل الجهاز متوقف، أم العملية، أم الشبكة، أم خدمة تابعة؟

## من الإنترنت إلى التطبيق

خلّينا نتتبع طلبًا من أول دخوله للبنية الخلفية لحد رجوع النتيجة:

```text
Network
   ↓
Load Balancer
   ↓
Web Server (Nginx/Apache)
   ├── Static File → Response
   └── Dynamic PHP → PHP-FPM
                         ↓
                    Application
                    ↙    ↓     ↘
                 Cache Database External API
                         ↓
                      Response
```

كل طبقة اختيارية ويمكن دمج عدة أدوار على جهاز واحد في مشروع صغير.

## توزيع الشغل بين الخوادم

**Load Balancer — موازن الأحمال** وسيط يختار نسخة من الخدمة لكل اتصال أو طلب. **Backend أوUpstream** اسم للخادم الذي يمرر إليه الوسيط الطلب. **Layer 4** هنا مستوى النقل الذي يتعامل مع TCP (Transmission Control Protocol؛ نقل بايتات بترتيب مع معالجة الفقد، مع احتمال فشل الاتصال) وUDP (User Datagram Protocol؛ نقل رسائل مستقلة بلا ضمان مدمج لوصولها أو ترتيبها)، و**Layer 7** مستوى التطبيق الذي يفهم HTTP (Hypertext Transfer Protocol؛ قواعد طلب الموارد والرد عليها في الويب)؛ الأرقام من نموذج OSI (Open Systems Interconnection؛ نموذج تعليمي يقسم أدوار الاتصال إلى سبع طبقات)، نموذج تعليمي يقسم الاتصال لسبع مسؤوليات.

**Health check — فحص الجاهزية** طلب صغير للتأكد أن الخدمة تستجيب. **Round-robin** يوزع بالتناوب، و**Least-connections** يختار الأقل اتصالات نشطة. **Sticky sessions** تحاول إبقاء المستخدم على نفس النسخة؛ **Shared session store** يحفظ بيانات الجلسات في مكان تشترك فيه النسخ.

**TLS (Transport Layer Security؛ قواعد حماية الاتصال بالتشفير والتحقق) termination — إنهاء TLS عند الوسيط** يعني أن الوسيط يفك حماية الاتصال الوارد. الاتصال التالي يحتاج قرار حماية مستقلًا؛ تشفير المتصفح لا يعني تلقائيًا تشفير كل الوصلات الداخلية.

موازن الحمل قد يرفع السعة والتوافر، ويضيف forwarding headers، أي حقولًا توضح معلومات الطلب الأصلي.

:::caution
لا تثق في `X-Forwarded-For` من أي عميل مباشرة. اضبط قائمة trusted proxies (وسطاء محددون تثق في المعلومات التي يضيفونها)، وإلا يمكن تزوير عنوان العميل.
:::

أمثلة: Nginx/HAProxy أو خدمات سحابية مثل AWS Elastic Load Balancing. والـLoad Balancer ليس بديلًا لقاعدة البيانات أو كود التطبيق.

## Web Server وVirtual Host

يستقبل Nginx أو Apache الاتصال ويختار الموقع باستخدام IP/port (منفذ منطقي برقم يميز جهة استقبال في بروتوكول النقل) واسم `Host` أو SNI (Server Name Indication؛ حقل في بداية TLS يحدد اسم الخادم المطلوب)/TLS configuration.

- **Static file:** صورة أو CSS (Cascading Style Sheets؛ قواعد مظهر عناصر الصفحة) أو JS (اختصار JavaScript، لغة برمجة لتعليمات وتفاعل الصفحة) يمكن إعادته مباشرة، مع Cache (نسخة محفوظة لتقليل تكرار القراءة أو الحساب) وCompression (ضغط: تمثيل نفس المحتوى ببيانات أقل في ضغط الويب المعتاد).
- **Dynamic (ديناميكي: نتيجة يبنيها البرنامج عند الطلب) PHP (اسم لغة برمجة تستخدم كثيرًا لمعالجة طلبات الويب على الخادم):** يُمرر إلى PHP runtime (بيئة تنفيذ اللغة والخدمات التي تحتاجها؛ غير معنى وقت التشغيل الزمني)، غالبًا PHP-FPM (PHP FastCGI Process Manager؛ برنامج يدير عمليات PHP التي تستقبل عملًا من خادم الويب) عبر FastCGI.
- **Reverse proxy:** قد يمرر الطلب إلى خدمة أخرى.

:::note[تصحيح]
Nginx لا ينفذ PHP داخل عمليته. يمرر الطلب إلى PHP-FPM ثم يستقبل الناتج. Apache يمكن أن يستخدم PHP-FPM أيضًا أو إعدادات أخرى.
:::

**PHP** لغة تُستخدم كثيرًا لبرامج الخادم. **PHP-FPM، PHP FastCGI Process Manager** برنامج يدير عمليات PHP الجاهزة لمعالجة الطلبات. **FastCGI** قواعد تبادل الطلب والرد بين خادم الويب وبيئة تنفيذ التطبيق؛ مش نفس بروتوكول المتصفح. **Worker (وحدة تنفيذ تتولى مهمة أو طلبًا؛ قد تكون عملية أو خيطًا حسب النظام)** هنا عملية جاهزة لمعالجة طلب، ومش لازم عامل طابور في الخلفية.

## PHP-FPM والتطبيق

يدير PHP-FPM مجموعة workers. يستقبل FastCGI parameters والطلب، يشغّل entry point مثل `public/index.php`، ثم يعيد headers (حقل أو مقدمة معلومات تضاف للبيانات بحسب الطبقة)/body (جسم الرسالة: المحتوى المرسل مثل نص صفحة أو بيانات طلب) لخادم الويب.

**Entry point — نقطة الدخول** الملف الذي تبدأ منه معالجة التطبيق. **Route — المسار البرمجي** قاعدة تربط عنوان الطلب بالكود المناسب. **Middleware — خطوة وسيطة** تنفذ فحصًا مشتركًا قبل المعالج أو بعده، مثل التحقق من تسجيل الدخول. **Business logic — قواعد التطبيق** تحدد ما الذي يفترض أن يحصل، مثل حساب سعر طلب. **Queue — طابور عمل** يحفظ مهام لمعالجتها لاحقًا.

التطبيق بدوره:

1. يطابق Route.
2. يشغّل Middleware.
3. يتحقق من المدخلات والمصادقة والصلاحيات.
4. ينفذ business logic.
5. يستخدم Database/Cache/Queue/API (Application Programming Interface؛ اتفاق يسمح لبرنامج بطلب بيانات أو عملية من مكوّن آخر) عند الحاجة.
6. يبني Response (رد: رسالة النتيجة التي يعيدها الخادم).

```php
<?php
declare(strict_types=1);

header('Content-Type: application/json; charset=utf-8');

try {
    $product = ['id' => 42, 'name' => 'Keyboard'];
    echo json_encode($product, JSON_THROW_ON_ERROR);
} catch (Throwable $e) {
    error_log($e);
    http_response_code(500);
    echo json_encode(['error' => 'Internal server error']);
}
```

لا ترسل stack trace (سلسلة استدعاءات توضح أين مر التنفيذ عند الخطأ) أو كلمات مرور قاعدة البيانات للمستخدم.

## رجوع الاستجابة

تعود النتيجة إلى Web Server ثم Load Balancer/CDN (Content Delivery Network؛ شبكة خوادم تقدم المحتوى من نقاط موزعة قرب المستخدمين) ثم الشبكة والمتصفح. قد تضيف طبقات وسيطة headers أو compression أو caching.

راقب:

- `Content-Type` الصحيح.
- Status code (رقم يصف نتيجة معالجة طلب HTTP) الصحيح.
- `Cache-Control` للبيانات الخاصة والعامة.
- Security headers (حقول رد تضبط سلوك حماية في المتصفح حسب نوع كل حقل) الملائمة.
- Request ID (معرّف يميز طلبًا لتتبع أحداثه) لتتبع نفس الطلب في logs (سجلات أحداث وتشخيص يكتبها البرنامج) عبر الخدمات.
- زمن كل طبقة، لا زمن PHP فقط.

## حالات مهمة

### Cache hit

```text
Browser/CDN Cache → response
PHP and database are skipped
```

### Static file

```text
Nginx → /public/app.css → response
PHP is skipped
```

### Dynamic request

```text
Nginx → PHP-FPM → App → Database → response
```

### فشل backend

قد يعيد proxy (وسيط يستقبل اتصالًا أو طلبًا ويمرره لجهة أخرى) حالة `502 Bad Gateway` عندما لا يحصل على استجابة صحيحة من upstream، أو `504 Gateway Timeout` عند انتهاء المهلة. أما `500` فعادة خطأ داخل التطبيق/الخادم الذي عالج الطلب.

## تدريب نهائي

1. افتح Network tab وسجّل method (طريقة الطلب: نوع العملية المطلوبة مثل القراءة) وstatus وcontent type.
2. أعد تحميل الصفحة ولاحظ `304` أو `from memory cache`.
3. أضف ملف CSS ثابتًا وendpoint (عنوان يقدم عملية أو بيانات من التطبيق) PHP ديناميكيًا وقارن.
4. أرسل request ID في header وسجله داخل PHP.
5. ارسم مسارك الفعلي وحدد الطبقات غير الموجودة بدل نسخ المخطط حرفيًا.

## المهلات واستهلاك الموارد

**Timeout — مهلة انتظار** حد زمني للعمل أو انتظار الرد. لو مهلة العميل ثانيتين، مثال ميزانية ممكنة: نخصص 0.6 ثانية لاستعلام البيانات، وننهي عمل التطبيق خلال 1.3 ثانية، ويوقف الوسيط الانتظار عند 1.6 ثانية، فيتبقى وقت لنقل الرد. دي حدود تصميم توضيحية تُراجع بالقياس، ومش مدد نجمعها كلها كأنها خطوات متتابعة؛ جزء منها يحيط بعمل أجزاء أخرى. إغلاق اتصال العميل لا يوقف عمل الخادم دائمًا تلقائيًا.

لو كل عمليات PHP-FPM مشغولة، طلب جديد قد ينتظر في طابور. زيادة عددها بلا حساب RAM قد تنتهي بـ**OOM، Out Of Memory**، أي عدم كفاية الذاكرة. **Unix socket** قناة اتصال محلية بين عمليات على نفس النظام، بينما TCP يصلح لاتصال محلي أو بين أجهزة. الحاوية Container بيئة تشغيل معزولة نسبيًا لتطبيق، وقد تتصل بحاوية أخرى عبر TCP.

**تدريب محلول:** الوسيط يعطي 504 بعد ثانية بينما التطبيق يحتاج 1.5 ثانية. أول سؤال هل المعالجة نفسها بطيئة أم المهلة أقصر من العقد المطلوب؟ راجع التوقيت في السجلات ثم اضبط الميزانية؛ رفع كل المهلات بلا قياس قد يخفي عطلًا ويزيد الطلبات المنتظرة.

## ماذا يحدث بعد الضغط على Enter؟

1. يحلل المتصفح الرابط ويفحص الـcache (نسخة محفوظة لتقليل تكرار القراءة أو الحساب) والسياسات المحلية.
2. يحوّل DNS اسم المضيف إلى عنوان IP إذا لم توجد إجابة مخزنة.
3. يختار نظام التشغيل واجهة الشبكة والمسار، وتتحرك البيانات عبر Wi-Fi (اتصال لاسلكي بالشبكة المحلية؛ لا يضمن اتصالها بالإنترنت) أو Ethernet (معيار شائع للاتصال على شبكة محلية سلكية) والراوتر والـISP (Internet Service Provider؛ شركة أو جهة توفر الاتصال بالإنترنت).
4. يُنشأ TCP (Transmission Control Protocol؛ نقل بايتات بترتيب مع معالجة الفقد، مع احتمال فشل الاتصال) connection لـHTTP/1.1 أو HTTP/2، أو اتصال QUIC (اسم بروتوكول نقل فوق UDP يضيف تدفقات موثوقة وحماية اتصال) فوق UDP (User Datagram Protocol؛ نقل رسائل مستقلة بلا ضمان مدمج لوصولها أو ترتيبها) لـHTTP/3.
5. مع HTTPS تتم TLS (Transport Layer Security؛ قواعد حماية الاتصال بالتشفير والتحقق) handshake (مصافحة: رسائل البداية للاتفاق على الاتصال) للتحقق من هوية الخادم وإنشاء قناة مشفرة.
6. يرسل المتصفح HTTP Request يحتوي method (طريقة الطلب: نوع العملية المطلوبة مثل القراءة) وpath (مسار المورد داخل العنوان، مثل /products) وheaders (حقل أو مقدمة معلومات تضاف للبيانات بحسب الطبقة)، وقد يحتوي body (جسم الرسالة: المحتوى المرسل مثل نص صفحة أو بيانات طلب).
7. قد يستقبل الطلب CDN (Content Delivery Network؛ شبكة خوادم تقدم المحتوى من نقاط موزعة قرب المستخدمين) أو WAF (Web Application Firewall؛ نظام يفحص طلبات الويب ويطبق قواعد حماية) أو load balancer (موازن أحمال يوزع العمل على نسخ خدمة) قبل الخادم الأصلي.
8. يعيد web server (خادم ويب يستقبل طلبات الويب ويعيد ملفات أو يمرر العمل للتطبيق) ملفًا ثابتًا، أو يمرر الطلب الديناميكي إلى تطبيق مثل PHP (اسم لغة برمجة تستخدم كثيرًا لمعالجة طلبات الويب على الخادم) عبر PHP-FPM (PHP FastCGI Process Manager؛ برنامج يدير عمليات PHP التي تستقبل عملًا من خادم الويب).
9. يتحقق التطبيق من المدخلات والهوية والصلاحيات، وقد يقرأ cache أو database (قاعدة بيانات: تخزين منظم يمكن البحث فيه وتعديله بقواعد).
10. تعود HTTP Response (رد: رسالة النتيجة التي يعيدها الخادم) وفيها status code (رقم يصف نتيجة معالجة طلب HTTP) وheaders وbody، ثم يفسر المتصفح المحتوى ويعرضه.

## من المسؤول عن ماذا؟

| المكوّن | مسؤوليته الأساسية |
|---|---|
| Browser أو Client | بناء الطلب، وإدارة cache/cookies، وتفسير الاستجابة |
| DNS | تحويل الاسم إلى عناوين مناسبة |
| TCP أو QUIC | نقل البيانات وخصائص الاتصال |
| TLS | التشفير، وسلامة البيانات، والتحقق من هوية الخادم |
| HTTP | معنى الطلب والاستجابة |
| Web server | استقبال HTTP، وخدمة الملفات الثابتة، وتمرير العمل الديناميكي |
| PHP | منطق التطبيق وبناء الاستجابة |
| Database | حفظ البيانات واسترجاعها |
