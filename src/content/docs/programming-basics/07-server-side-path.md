## خادم واحد يوضح الفكرة

ابدأ بالتتبع الجاهز ده من غير تثبيت Node.js. **Route — مسار معالجة** قاعدة تربط عنوانًا بعمل ينفذه البرنامج؛ وJSON صيغة نصية لحقول وقيم. دي بيانات تعليمية للقراءة، مش خرج قسناه من جهازك:

| المدخل | عمل server | الرد |
|---|---|---|
| GET `/api/products/1` | يختار المنتج 1 ويكوّن JSON | 200 مع بيانات المنتج |
| GET `/api/products/2` | نفس نوع المسار، لكن المنتج غير موجود | 404 مع وصف غياب المنتج |

تطبيق Node.js في [المعمل المحلي](/programming-basics/32-local-network-lab/) اختياري: لو جهزته، افتح المسارين على 8766 وقارن المتوقع. ولو اخترت PHP، التجربة الكاملة داخل الدرس تحت لا تحتاج Node.

```text
Browser → one server → choose route → build response → Browser
```

افحص سطر الطلب في الطرفية واربطه بالحالة في Network. دلوقتي عندنا سبب لفهم كل مرحلة. الوسيط في الدرس التالي يضيف جهة أخرى أمام هذا server؛ مش شرطًا لعمل أول طلب.

## قبل التفاصيل

هذا الدرس يتتبع الطلب بعد وصوله إلى البنية الخلفية. الهدف ليس حفظ أسماء الأدوات، بل معرفة حدود المسؤولية حتى تبحث عن العطل في الطبقة الصحيحة.

## ما server؟

كلمة **Server** تصف دورًا، لا شكل جهاز بعينه. قد تعني:

- **جهازًا فعليًا أو Virtual Machine (جهاز افتراضي: بيئة تحاكي جهازًا وتشغل نظامًا وتطبيقات)** يوفّر CPU (Central Processing Unit؛ المعالج الرئيسي الذي ينفذ التعليمات) وRAM (Random Access Memory؛ ذاكرة العمل التي تحمل بيانات وتعليمات البرامج النشطة) وشبكة وتخزينًا.
- **برنامجًا** يستمع على عنوان IP (Internet Protocol؛ قواعد عنونة الحزم وتوجيهها بين الشبكات، وعنوان IP رقم يحدد واجهة في هذا السياق) ومنفذ ويجيب وفق Protocol، مثل Nginx أو PostgreSQL.
- **دورًا في تفاعل محدد:** البرنامج الذي يطلب خدمة هو Client، والذي يقدمها Server. وقد يكون التطبيق نفسه Client لخادم قاعدة البيانات.

يبدأ Server Process (عملية: نسخة برنامج تعمل بذاكرة وحالة وموارد) عادة بفتح Socket (واجهة اتصال ينشئها البرنامج؛ نقطة شبكة منها ترتبط عادة ببروتوكول وعنوان ومنفذ) وربطه بعنوان ومنفذ ثم الاستماع. عندما يصل اتصال، يقرأ الطلب ويتحقق منه وينفذ العمل ويرسل استجابة.

تشغيل `localhost:8000` لا يعني وجود جهاز مستقل؛ يعني أن Process على جهازك يستمع محليًا على المنفذ `8000`.

يمكن لجهاز واحد تشغيل Web Server (خادم ويب يستقبل طلبات الويب ويعيد ملفات أو يمرر العمل للتطبيق) وApplication Server (برنامج يشغّل منطق التطبيق ويبني نتيجته) وDatabase (قاعدة بيانات: تخزين منظم يمكن البحث فيه وتعديله بقواعد) في التطوير، بينما تفصلها بيئة الإنتاج لأسباب التوسع والعزل والأمان.

وعبارة «server وقع» غير دقيقة حتى نحدد: هل الجهاز متوقف، أم العملية، أم الشبكة، أم خدمة تابعة؟

## من الإنترنت إلى التطبيق

خلّينا نتتبع طلب منتج موجود، ونفترض هنا إن بياناته محفوظة في قاعدة بيانات:

1. browser يرسل طلب HTTP. لو فيه **CDN — شبكة تقدم نسخ المحتوى من نقاط موزعة** أو Load Balancer، قد يمر عليهما أولًا؛ وجودهما اختياري. وقد يرد CDN من نسخته من غير الوصول للتطبيق.
2. عند وصول الطلب للخادم الأصلي، دور Web Server يستقبل HTTP. لو المطلوب ملف ثابت، يقرأه ويرده مباشرة؛ لو طلبًا ديناميكيًا، يسلّمه لبيئة تنفيذ التطبيق.
3. في إعداد PHP شائع: Nginx يمرر العمل عبر FastCGI إلى PHP-FPM. التطبيق يختار Route ويطلب سجل المنتج من قاعدة البيانات **لو محتاجها**؛ مش كل تطبيق أو طلب له قاعدة بيانات.
4. قاعدة البيانات تعيد السجل **للتطبيق**، مش للمتصفح. التطبيق يبني الرد، ثم يرجع عبر runtime (المكونات والخدمات اللي بتدير تنفيذ كود اللغة) وخادم الويب وأي وسطاء موجودين إلى browser.

دور استقبال HTTP (قواعد تبادل request وresponse بين client وserver) لازم لرد ويب، ودور تنفيذ منطق التطبيق لازم للطلب الديناميكي، لكن ممكن برنامج واحد يجمع الدورين، زي خادم PHP المحلي في التجربة تحت. مش لازم كل دور يبقى جهازًا أو خدمة منفصلة. CDN وموازن الحمل وقاعدة البيانات أدوات حسب الحاجة، مش مراحل إجبارية في كل رحلة.

## توزيع الشغل بين الخوادم

**Load Balancer — موازن الأحمال** وسيط يختار نسخة من الخدمة لكل اتصال أو طلب. **Backend أو Upstream** اسم للخادم الذي يمرر إليه الوسيط الطلب.

**Layer 4** هنا مستوى النقل الذي يتعامل مع TCP (Transmission Control Protocol؛ نقل بايتات بترتيب مع معالجة الفقد، مع احتمال فشل الاتصال) وUDP (User Datagram Protocol؛ نقل رسائل مستقلة بلا ضمان مدمج لوصولها أو ترتيبها)، و**Layer 7** مستوى التطبيق الذي يفهم HTTP (Hypertext Transfer Protocol؛ قواعد طلب الموارد والرد عليها في الويب)؛ الأرقام من نموذج OSI (Open Systems Interconnection)، نموذج تعليمي يقسم مسؤوليات الاتصال إلى سبع طبقات.

**Health check — فحص الجاهزية** طلب صغير للتأكد أن الخدمة تستجيب. **Round-robin** يوزع بالتناوب، و**Least-connections** يختار الأقل اتصالات نشطة. **Sticky sessions** تحاول إبقاء المستخدم على نفس النسخة؛ **Shared session store** يحفظ بيانات الجلسات في مكان تشترك فيه النسخ.

**TLS (Transport Layer Security؛ قواعد حماية الاتصال بالتشفير والتحقق) termination — إنهاء TLS عند الوسيط** يعني أن الوسيط يفك حماية الاتصال الوارد. الاتصال التالي يحتاج قرار حماية مستقلًا؛ تشفير browser لا يعني تلقائيًا تشفير كل الوصلات الداخلية.

موازن الحمل قد يرفع السعة والتوافر، ويضيف forwarding headers، أي حقولًا توضح معلومات الطلب الأصلي.

:::caution
لا تثق في `X-Forwarded-For` من أي عميل مباشرة. اضبط قائمة trusted proxies (وسطاء محددون تثق في المعلومات التي يضيفونها)، وإلا يمكن تزوير عنوان العميل.
:::

أمثلة: Nginx/HAProxy أو خدمات سحابية مثل AWS Elastic Load Balancing. والـLoad Balancer ليس بديلًا لقاعدة البيانات أو كود التطبيق.

## Web Server وVirtual Host

يستقبل Nginx أو Apache الاتصال ويختار الموقع باستخدام IP/port (منفذ منطقي برقم يميز جهة استقبال في بروتوكول النقل) واسم `Host` أو SNI (Server Name Indication؛ حقل في بداية TLS يحدد اسم server المطلوب)/TLS configuration.

- **Static file:** صورة أو CSS (Cascading Style Sheets؛ قواعد مظهر عناصر الصفحة) أو JS (اختصار JavaScript، لغة برمجة لتعليمات وتفاعل الصفحة) يمكن إعادته مباشرة، مع Cache (نسخة محفوظة لتقليل تكرار القراءة أو الحساب) وCompression (ضغط: تمثيل نفس المحتوى ببيانات أقل في ضغط الويب المعتاد).
- **Dynamic (ديناميكي: نتيجة يبنيها البرنامج عند الطلب) PHP (اسم لغة برمجة تستخدم كثيرًا لمعالجة طلبات الويب على server):** يُمرر إلى PHP runtime (بيئة تنفيذ اللغة والخدمات التي تحتاجها؛ غير معنى runtime الزمني)، غالبًا PHP-FPM (PHP FastCGI Process Manager؛ برنامج يدير عمليات PHP التي تستقبل عملًا من خادم الويب) عبر FastCGI.
- **Reverse proxy:** قد يمرر الطلب إلى خدمة أخرى.

:::note[تصحيح]
Nginx لا ينفذ PHP داخل عمليته. يمرر الطلب إلى PHP-FPM ثم يستقبل الناتج. Apache يمكن أن يستخدم PHP-FPM أيضًا أو إعدادات أخرى.
:::

**PHP** لغة تُستخدم كثيرًا لبرامج server. **PHP-FPM، PHP FastCGI Process Manager** برنامج يدير عمليات PHP الجاهزة لمعالجة الطلبات. **FastCGI** قواعد تبادل الطلب والرد بين خادم الويب وبيئة تنفيذ التطبيق؛ مش نفس بروتوكول browser.

**Worker (وحدة تنفيذ تتولى مهمة أو طلبًا؛ قد تكون عملية أو خيطًا حسب النظام)** هنا عملية جاهزة لمعالجة طلب، ومش لازم عامل طابور في الخلفية.

## PHP-FPM والتطبيق

يدير PHP-FPM مجموعة workers. يستقبل FastCGI parameters والطلب، يشغّل entry point مثل `public/index.php`، ثم يعيد headers (حقل أو مقدمة معلومات تضاف للبيانات بحسب الطبقة)/body (جسم الرسالة: المحتوى المرسل مثل نص صفحة أو بيانات طلب) لخادم الويب.

**Entry point — نقطة الدخول** الملف الذي تبدأ منه معالجة التطبيق. **Route — المسار البرمجي** قاعدة تربط عنوان الطلب بالكود المناسب. **Middleware — خطوة وسيطة** تنفذ فحصًا مشتركًا قبل المعالج أو بعده، مثل التحقق من تسجيل الدخول.

**Business logic — قواعد التطبيق** تحدد ما الذي يفترض أن يحصل، مثل حساب سعر طلب. **Queue — طابور عمل** يحفظ مهام لمعالجتها لاحقًا.

التطبيق بدوره:

1. يطابق Route.
2. يشغّل Middleware.
3. يتحقق من المدخلات والمصادقة والصلاحيات.
4. ينفذ business logic.
5. يستخدم Database/Cache/Queue/API (Application Programming Interface؛ اتفاق يسمح لبرنامج بطلب بيانات أو عملية من مكوّن آخر) عند الحاجة.
6. يبني Response (رد: رسالة النتيجة التي يعيدها server).

### تجربة PHP اختيارية: نجاح وفشل قابلان للتكرار

بعد [تجهيز PHP](/php/00-lab-setup/)، احفظ الملف الكامل التالي باسم `product.php` في مجلد تدريب جديد. لا يحتاج Node.js أو Nginx. **Exception — استثناء** إشارة فشل تلتقطها `try/catch`؛ و`Throwable` نوع للأخطاء القابلة للالتقاط. `RuntimeException` يصنع الفشل التعليمي المقصود.

`$_GET` تحمل معاملات الرابط، و`?? ''` تعطي نصًا فارغًا عند غياب المعامل. `fail=1` مفتاح معمل فقط، مش صلاحية أو إعداد إنتاج. `header` تكتب حقل رد، و`json_encode` تحول قيم PHP إلى JSON.

```php
<?php
declare(strict_types=1);

header('Content-Type: application/json; charset=utf-8');
header('Cache-Control: no-store');

try {
    if (($_GET['fail'] ?? '') === '1') {
        throw new RuntimeException('Deliberate local failure for the foundations lab');
    }
    $product = ['id' => 42, 'name' => 'Keyboard'];
    echo json_encode($product, JSON_THROW_ON_ERROR);
} catch (Throwable $e) {
    error_log((string) $e);
    http_response_code(500);
    echo json_encode(['error' => 'Internal server error']);
}
```

`(string) $e` يحول كائن exception لنص قبل `error_log`؛ من غير التحويل، strict typing قد يجعل تسجيل الخطأ نفسه يرمي TypeError. **Log — سجل حدث** هنا خرج server في الطرفية. `JSON_THROW_ON_ERROR` يطلب استثناء عند فشل الترميز، و`http_response_code` يحدد رمز الرد.

شغّل من مجلد التدريب:

~~~powershell
php -S 127.0.0.1:8089
~~~

`-S` يبدأ خادم تطوير على جهازك فقط، مش خدمة إنتاج. من طرفية ثانية:

~~~powershell
curl.exe -i http://127.0.0.1:8089/product.php
curl.exe -i "http://127.0.0.1:8089/product.php?fail=1"
~~~

`-i` يعرض الرؤوس والجسم. استخدم `curl` بدل `curl.exe` على Linux وmacOS. المتوقع 200 مع `{"id":42,"name":"Keyboard"}`، ثم 500 مع `{"error":"Internal server error"}` فقط. سبب الفشل و**Stack (بنية تتعامل مع آخر عنصر دخل أولًا؛ call stack تتتبع الاستدعاءات النشطة) trace — سلسلة مواضع التنفيذ عند الخطأ** يظهران في طرفية server، لا في جسم رد العميل. كرر الطلب الأول بعد الفشل: يرجع 200 من جديد.

أوقف server بـCtrl+C. لا تنشر مفتاح الفشل ده، ولا ترفع سجلات قد تحتوي أسرارًا. المثال يوضح ردًا عامًا وسجلًا خاصًا، مش API (عقد يحدد إزاي برنامج يطلب بيانات أوعملية من برنامج أوجزء آخر) منتجات كاملة.

لا ترسل stack trace (سلسلة استدعاءات توضح أين مر التنفيذ عند الخطأ) أو كلمات مرور قاعدة البيانات للمستخدم.

## رجوع الاستجابة

تعود النتيجة إلى Web Server ثم Load Balancer/CDN (Content Delivery Network؛ شبكة خوادم تقدم المحتوى من نقاط موزعة قرب المستخدمين) ثم الشبكة وbrowser. قد تضيف طبقات وسيطة headers أو compression أو caching.

راقب:

- `Content-Type` الصحيح.
- Status code (رقم يصف نتيجة معالجة طلب HTTP) الصحيح.
- `Cache-Control` للبيانات الخاصة والعامة.
- Security headers (حقول رد تضبط سلوك حماية في browser حسب نوع كل حقل) الملائمة.
- Request ID (معرّف يميز طلبًا لتتبع أحداثه) لتتبع نفس الطلب في logs (سجلات أحداث وتشخيص يكتبها البرنامج) عبر الخدمات.
- زمن كل طبقة، لا زمن PHP فقط.

## حالات مهمة

### Cache hit

```text
Browser/CDN Cache → response
PHP and database are skipped
```

### Static file

```text
Nginx → /public/app.css → response
PHP is skipped
```

### Dynamic request

```text
Nginx → PHP-FPM → App
App → Database: query
Database → App: result
App → PHP-FPM → Nginx → Client: response
```

### فشل backend

قد يعيد proxy (وسيط يستقبل اتصالًا أو طلبًا ويمرره لجهة أخرى) حالة `502 Bad Gateway` عندما لا يحصل على استجابة صحيحة من upstream، أو `504 Gateway Timeout` عند انتهاء المهلة. أما `500` فعادة خطأ داخل التطبيق/server الذي عالج الطلب.

## تدريب نهائي

1. افتح Network tab وسجّل method (طريقة الطلب: نوع العملية المطلوبة مثل القراءة) وstatus وcontent type.
2. أعد تحميل `product.php`: المثال يرسل `Cache-Control: no-store`، فلا تنتظر `304` أو `from memory cache` منه. لو بتقارن سلوك التخزين، استخدم تجربة [درس الكاش](/programming-basics/10-http-caching-compression/) بإعداداتها المحددة.
3. أضف ملف CSS ثابتًا وendpoint (عنوان يقدم عملية أو بيانات من التطبيق) PHP ديناميكيًا وقارن.
4. أرسل request ID في header وسجله داخل PHP.
5. ارسم مسارك الفعلي وحدد الطبقات غير الموجودة بدل نسخ المخطط حرفيًا.

## المهلات واستهلاك الموارد

**Timeout — مهلة انتظار** حد زمني للعمل أو انتظار الرد. لو مهلة العميل ثانيتين، مثال ميزانية ممكنة: نخصص 0.6 ثانية لاستعلام البيانات، وننهي عمل التطبيق خلال 1.3 ثانية، ويوقف الوسيط الانتظار عند 1.6 ثانية، فيتبقى وقت لنقل الرد.

دي حدود تصميم توضيحية تُراجع بالقياس، ومش مدد نجمعها كلها كأنها خطوات متتابعة؛ جزء منها يحيط بعمل أجزاء أخرى. إغلاق اتصال العميل لا يوقف عمل server دائمًا تلقائيًا.

لو كل عمليات PHP-FPM مشغولة، طلب جديد قد ينتظر في طابور. زيادة عددها بلا حساب RAM قد تنتهي بـ**OOM، Out Of Memory**، أي عدم كفاية الذاكرة. **Unix socket** قناة اتصال محلية بين عمليات على نفس النظام، بينما TCP يصلح لاتصال محلي أو بين أجهزة. الحاوية Container بيئة تشغيل معزولة نسبيًا لتطبيق، وقد تتصل بحاوية أخرى عبر TCP.

**تدريب محلول:** الوسيط يعطي 504 بعد ثانية بينما التطبيق يحتاج 1.5 ثانية. أول سؤال هل المعالجة نفسها بطيئة أم المهلة أقصر من العقد المطلوب؟ راجع التوقيت في السجلات ثم اضبط الميزانية؛ رفع كل المهلات بلا قياس قد يخفي عطلًا ويزيد الطلبات المنتظرة.

## ماذا يحدث بعد الضغط على Enter؟

1. يحلل browser الرابط ويفحص الـcache (نسخة محفوظة لتقليل تكرار القراءة أو الحساب) والسياسات المحلية.
2. يحوّل DNS (نظام يجيب عن أسئلة أسماء المواقع، ومنها عناوين IP) اسم المضيف إلى عنوان IP إذا لم توجد إجابة مخزنة.
3. يختار Operating System (software بيدير موارد الجهاز ويقدم خدمات للبرامج) واجهة الشبكة والمسار، وتتحرك البيانات عبر Wi-Fi (اتصال لاسلكي بالشبكة المحلية؛ لا يضمن اتصالها بالإنترنت) أو Ethernet (معيار شائع للاتصال على شبكة محلية سلكية) والراوتر والـISP (Internet Service Provider؛ شركة أو جهة توفر الاتصال بالإنترنت).
4. يُنشأ TCP (Transmission Control Protocol؛ نقل بايتات بترتيب مع معالجة الفقد، مع احتمال فشل الاتصال) connection لـHTTP/1.1 أو HTTP/2، أو اتصال QUIC (اسم بروتوكول نقل فوق UDP يضيف تدفقات موثوقة وحماية اتصال) فوق UDP (User Datagram Protocol؛ نقل رسائل مستقلة بلا ضمان مدمج لوصولها أو ترتيبها) لـHTTP/3.
5. مع HTTPS (استخدام HTTP عبر اتصال محمي بـTLS) تتم TLS (Transport Layer Security؛ قواعد حماية الاتصال بالتشفير والتحقق) handshake (مصافحة: رسائل البداية للاتفاق على الاتصال) للتحقق من هوية server وإنشاء قناة مشفرة.
6. يرسل browser HTTP Request يحتوي method (طريقة الطلب: نوع العملية المطلوبة مثل القراءة) وpath (مسار المورد داخل العنوان، مثل /products) وheaders (حقل أو مقدمة معلومات تضاف للبيانات بحسب الطبقة)، وقد يحتوي body (جسم الرسالة: المحتوى المرسل مثل نص صفحة أو بيانات طلب).
7. قد يستقبل الطلب CDN (Content Delivery Network؛ شبكة خوادم تقدم المحتوى من نقاط موزعة قرب المستخدمين) أو WAF (Web Application Firewall؛ نظام يفحص طلبات الويب ويطبق قواعد حماية) أو load balancer (موازن أحمال يوزع العمل على نسخ خدمة) قبل server الأصلي.
8. يعيد web server (خادم ويب يستقبل طلبات الويب ويعيد ملفات أو يمرر العمل للتطبيق) ملفًا ثابتًا، أو يمرر الطلب الديناميكي إلى تطبيق مثل PHP (اسم لغة برمجة تستخدم كثيرًا لمعالجة طلبات الويب على server) عبر PHP-FPM (PHP FastCGI Process Manager؛ برنامج يدير عمليات PHP التي تستقبل عملًا من خادم الويب).
9. يتحقق التطبيق من المدخلات والهوية والصلاحيات، وقد يقرأ cache أو database (قاعدة بيانات: تخزين منظم يمكن البحث فيه وتعديله بقواعد).
10. تعود HTTP Response (رد: رسالة النتيجة التي يعيدها server) وفيها status code (رقم يصف نتيجة معالجة طلب HTTP) وheaders وbody، ثم يفسر browser المحتوى ويعرضه.


:::note
دي احتمالات مختلفة للخطوات، مش طريقًا إجباريًا لكل طلب. قد يجيب browser cache أو CDN من غير الوصول إلى PHP، وقد لا يملك التطبيق الصغير load balancer أو database أصلًا.
:::

## من المسؤول عن ماذا؟

| المكوّن | مسؤوليته الأساسية |
|---|---|
| Browser أو Client | بناء الطلب، وإدارة cache/cookies، وتفسير الاستجابة |
| DNS | تحويل الاسم إلى عناوين مناسبة |
| TCP أو QUIC | نقل البيانات وخصائص الاتصال |
| TLS | التشفير، وسلامة البيانات، والتحقق من هوية server |
| HTTP | معنى الطلب والاستجابة |
| Web server | استقبال HTTP، وخدمة الملفات الثابتة، وتمرير العمل الديناميكي |
| PHP | منطق التطبيق وبناء الاستجابة |
| Database | حفظ البيانات واسترجاعها |
